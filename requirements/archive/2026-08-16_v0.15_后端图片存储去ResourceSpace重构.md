# artDatabase 后端图片存储去 ResourceSpace 重构

> 文档版本：v0.15  
> 文档日期：2026-08-16  
> 状态：需求澄清中  
> 依据：修订 v0.1 第 7 章「当前技术方向」与 v0.2 验证一中以 ResourceSpace 作为素材文件与缩略图存储的技术决策；本文档确立以原生 Node.js 自建图片存储取代 ResourceSpace 的方向。

## 1. 背景与目标

### 1.1 现状

当前应用整体运行在 Cloudflare Worker 上（vinext + wrangler），业务数据在 D1（SQLite）。图片二进制与缩略图由外部系统 ResourceSpace 承担，通过其 HTTP API 读写：

| 环节 | 现状实现 | 涉及文件 |
| --- | --- | --- |
| 上传 | `create_resource` → `upload_multipart` → `update_field` | `db/resourcespace.ts`、`app/api/uploads/route.ts` |
| 原图/缩略图读取 | `get_resource_data` → `get_resource_path` → fetch 转发 | `db/resourcespace.ts`、`app/api/media/route.ts` |
| 元数据更新 | `update_field`（title/keywords/caption/notes/artdatabasesourceurl） | `app/api/assets/route.ts` |
| 软删除 | `delete_resource`（移入回收站） | `app/api/assets/route.ts` |
| 恢复 | `put_resource_data`（archive=0） | `app/api/assets/restore/route.ts` |
| 彻底删除 | `delete_resource` 两次 | `app/api/assets/route.ts` |

已知事实：

1. 全部元数据（名称/标签/描述/备注/来源链接）**已同时保存在 D1 `assets` 表**，ResourceSpace 侧是冗余双写，去掉后不损失业务数据。
2. D1 `assets` 表已有 `storage_key`、`thumbnail_key` 两个字段，当前上传流程未使用，仅历史/种子素材使用过 R2（`MEDIA` bucket）。
3. 缩略图目前由客户端在 `UploadModal` 用 canvas 生成 webp 并随表单提交，但后端 `/api/uploads` **从未读取该缩略图字段**，实际缩略图来自 ResourceSpace。
4. 依赖项包括环境变量 `RS_BASE_URL`、`RS_API_USER`、`RS_API_KEY`，以及 `infra/resourcespace/`、`scripts/validation/resourcespace/` 一套验证环境。

### 1.2 目标

1. 用**原生 Node.js** 自建图片存储服务，承担原始图片与缩略图的写入、读取、删除。
2. **完全移除对 ResourceSpace 的依赖**：删除相关代码、配置、验证环境与文档索引中的技术方向，不再要求任何 RS 环境变量或服务。
3. 缩略图改为**服务端生成并存储**，客户端不再负责生成缩略图。
4. 图片二进制**落本地磁盘**，通过持久化卷保证重启后可用。
5. 保持对前端与业务 API 的**最小侵入**：`/api/media` 的 URL 契约不变，React 前端原则上无需改动。
6. 部署方式简单、依赖最少：存储服务为单容器、单卷，可部署到任意 VPS / Fly.io / Railway / Render。
7. 图片存储实现为**可插拔模块**：定义统一接口，后端实现可替换（默认本地磁盘，对象存储可后续添加），服务端按配置加载，调用方不感知后端差异。

### 1.3 非目标

- 不迁移前端 React/RSC 构建链，也不迁移 D1 数据库与现有业务 API 路由（项目/维度/画板等）。
- 不引入视频、音频等新素材类型。
- 不做对象存储抽象层、不做分布式多实例共享存储（MVP 单实例本地磁盘）。
- 不做存储层内容寻址去重（文件级去重仍由 D1 的 SHA-256 重复检查承担）。
- 不实现用户账号与权限（沿用 v0.1：局域网/内部用户无身份）。

## 2. 方案决策

### 2.1 候选方案对比

| 维度 | 方案 A：独立原生 Node.js 存储服务（推荐） | 方案 B：整个后端迁到 Node.js |
| --- | --- | --- |
| 改动范围 | 仅替换图片存储链路，Worker 业务与前端不变 | 连带迁移前端 RSC、全部 API 路由与 D1 数据库 |
| 新增依赖 | 仅 `sharp` | `node:http` + `sharp` + SQLite 驱动（或 `node:sqlite`）等 |
| 部署形态 | 一个容器 + 一个卷，与 Worker 并行 | 单进程容器（含前端静态资源 + API + 存储 + 数据库） |
| 风险 | 低，可灰度、可回退 | 高，前端与数据层同时切换 |
| 是否满足目标 | 满足 | 满足，但超出「去 ResourceSpace」所需范围 |

### 2.2 决策与理由

采用**方案 A**：保留现有 Worker 应用，新增独立原生 Node.js 图片存储服务。

- 需求聚焦「重构图片存储、去掉 ResourceSpace」，方案 A 精确覆盖且不拖入前端与数据库迁移的高风险工作。
- 存储服务无状态（文件在磁盘、元数据在 D1），接口少而稳定，易于部署到任意云。
- 前端通过现有 `/api/media` 继续取图，Worker 仅在服务端持有存储服务令牌，符合 v0.1「API 密钥不得发送到浏览器」的原则。
- 若未来确需单进程全栈部署（含 `node:sqlite`），可作为独立后续阶段，不在本需求内强制。
- 存储实现为**可插拔模块**：定义统一接口，后端可替换；默认实现为本地磁盘，未来可加对象存储后端而不改调用方。

## 3. 目标架构

```text
浏览器 ──HTTPS──▶ Cloudflare Worker（vinext）
                      │  业务 API（projects/dimensions/canvas/...）
                      ├─▶ D1（SQLite：业务数据 + 元数据 + storage_key/thumbnail_key）
                      │
                      │  /api/uploads   POST /v1/blobs
                      ├──────────────▶ 原生 Node.js 图片存储服务 ──▶ 本地磁盘卷
                      │  /api/media     GET  /v1/blobs/:id[/thumbnail]  （原图 + 缩略图）
                      └────────────────（Bearer Token 鉴权，仅 Worker 可访问）

（ResourceSpace 相关组件全部移除）
```

职责边界：

- **Worker 应用**：UI、业务 API、D1 元数据、重复检测、软删/恢复/彻底删的业务决策。
- **Node 图片存储服务**：纯二进制文件服务（写文件、读文件、生成缩略图、删文件），**不持有任何业务数据、不连数据库**。
- **D1**：素材记录与元数据、`storage_key`/`thumbnail_key`（指向存储服务中的 blob id）。

## 4. 原生 Node.js 图片存储服务设计

存储服务按**可插拔模块**实现：核心定义统一接口，后端（backend）负责真正读写文件；默认后端为本地磁盘，未来可替换为对象存储。对外表现为一个独立的 Node 进程，通过 HTTP 提供存取能力，Worker 经配置的地址调用。

### 4.1 运行环境与依赖

- 运行时：Node.js ≥ 22.13（与现有 `engines` 一致），使用 Web 标准 `Request`/`Response`/`FormData` 与 `ReadableStream`↔`Readable` 互转，无需 HTTP 框架。
- 仅使用 Node 内置模块：`node:http`、`node:fs`、`node:crypto`、`node:stream`、`node:path`、`node:os`。
- 唯一第三方运行时依赖：`sharp`（读取尺寸、生成缩略图）。
- 不引入：Express/Fastify、ORM、数据库驱动、multipart 解析库（用 `request.formData()` 与 `File`）。

### 4.2 目录布局

```text
<STORE_ROOT>/
  blobs/<id>        # 原始图片
  thumbs/<id>       # 缩略图（webp）
  tmp/              # 上传过程临时文件，启动时清理
```

- `<id>` 为服务端生成的随机 UUID（`crypto.randomUUID()`），与 D1 素材 `id` 无关。
- 一个素材对应一个 `blobs/<id>` 与一个 `thumbs/<id>`；即使多个素材字节相同也各自成文件（文件级去重留待后续，见 10 决策记录）。
- 路径由配置 `IMAGE_STORE_ROOT` 指定，**不硬编码**；未配置时默认 `<CWD>/data`。

### 4.3 HTTP 接口

除健康检查外，所有接口要求请求头 `Authorization: Bearer <IMAGE_STORE_TOKEN>`，不匹配返回 `401`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/health` | 健康检查，返回 `200`，无鉴权（供容器探活） |
| POST | `/v1/blobs` | multipart 上传，字段 `file`（必填）；返回 blob 元数据 |
| GET | `/v1/blobs/:id` | 返回原始图片（流式，含 content-type/content-length/etag/cache-control） |
| GET | `/v1/blobs/:id/thumbnail` | 返回缩略图 |
| HEAD | `/v1/blobs/:id` | 存在性检查，供补偿与探活 |
| DELETE | `/v1/blobs/:id` | 彻底删除原图与缩略图 |

`POST /v1/blobs` 返回体：

```json
{
  "id": "<uuid>",
  "sha256": "<64位hex>",
  "size": 1234567,
  "width": 1920,
  "height": 1080,
  "mimeType": "image/jpeg",
  "thumbnailId": "<uuid>",
  "thumbnailWidth": 900,
  "thumbnailHeight": 506
}
```

处理流程：写临时文件 → 计算 SHA-256 → `sharp` 读尺寸并生成缩略图 → 原子改名落入 `blobs/`、`thumbs/` → 返回元数据。任一环节失败即清理临时文件并返回 `4xx/5xx`，不留半成品。

### 4.4 鉴权

- 服务端常量比较令牌（用 `crypto.timingSafeEqual` 避免时序泄露）。
- 令牌经环境变量 `IMAGE_STORE_TOKEN` 注入，不写入代码与镜像，不发往浏览器。
- Worker 侧以同名字段持有令牌，仅服务端可见。

### 4.5 缩略图生成

- 服务端用 `sharp` 将原图缩放为**最长边 ≤ 900px（可配置 `IMAGE_STORE_THUMB_MAX`）**、保持宽高比的 WebP，质量默认 82。
- 与当前网格展示的视觉尺寸保持一致；显示端裁剪仍由 CSS `object-fit: cover` 完成，不改变存储内容。
- 缩略图与原图原子配套写入；上传成功后二者同时存在。

### 4.6 错误与补偿

- 存储服务自身失败必须抛出可辨识错误（含状态码），Worker 据此做补偿清理（见 6、9）。
- 上传失败不留临时文件或半成品 blob。
- 删除不存在 blob 视为成功（幂等）。

## 5. 应用后端改动

### 5.1 数据模型（D1）

字段语义调整（不改表结构，仅改使用方式）：

| 字段 | 新语义 |
| --- | --- |
| `assets.storage_key` | 原图 blob id（指向存储服务 `blobs/<id>`） |
| `assets.thumbnail_key` | 缩略图 blob id（指向 `thumbs/<id>`） |
| `assets.external_id` | 弃用，仅保留用于存量迁移读取（迁移后清空） |
| `assets.thumbnail_url` | 保留：种子素材外链（picsum）与可选外部 URL 回退 |

`getMediaBucket()`（`db/storage.ts`）与 R2 分支整体移除；媒体读取统一走存储服务。

### 5.2 各 API 路由改动清单

| 路由 | 改动 |
| --- | --- |
| `app/api/uploads/route.ts` | 移除 `createResourceSpaceAsset`/`permanentlyDeleteResourceSpaceAsset`；改为调用存储服务 `POST /v1/blobs`，将返回的 `id` 写入 `storage_key`、`thumbnailId` 写入 `thumbnail_key`；DB 写入失败时按 blob id 调用 `DELETE /v1/blobs/:id` 补偿 |
| `app/api/media/route.ts` | 移除 `fetchResourceSpaceMedia`；按 `storage_key`/`thumbnail_key` 调存储服务 `GET /v1/blobs/:id[/thumbnail]` 并透传响应；`thumbnail_url`（外链）作为无本地键时的回退 |
| `app/api/assets/route.ts` PATCH | 移除 `updateResourceSpaceMetadata`，仅保留 D1 `UPDATE assets` |
| `app/api/assets/route.ts` DELETE（软删） | 移除 `softDeleteResourceSpaceAsset`，仅置 `deleted_at` |
| `app/api/assets/route.ts` DELETE（彻底删） | 移除 `permanentlyDeleteResourceSpaceAsset` 与 R2 删除；改为对 `storage_key`/`thumbnail_key` 调存储服务 `DELETE`，再删 D1 行 |
| `app/api/assets/restore/route.ts` | 移除 `restoreResourceSpaceAsset`，仅清空 `deleted_at` |
| `db/resourcespace.ts` | 整个文件删除 |
| `db/storage.ts` | 整个文件删除（R2 分支不再使用） |
| `worker/index.ts` | 移除 `RS_*` 绑定类型，新增 `IMAGE_STORE_BASE_URL`、`IMAGE_STORE_TOKEN` |
| `.dev.vars.example` | 由 `RS_*` 替换为 `IMAGE_STORE_*` |

缩略图 URL 拼接处（`library`、`workspace`、`canvas` 三个路由中的 CASE 表达式）由：

```sql
WHEN a.external_id IS NOT NULL OR a.thumbnail_key IS NOT NULL
```

改为：

```sql
WHEN a.thumbnail_key IS NOT NULL OR a.storage_key IS NOT NULL
```

其余 SQL 不变。

### 5.3 前端改动（可选）

- `/api/media` 契约不变，前端 `AllAssetsView`、`ArtDatabaseApp`、`BoardView`、`DimensionPreview` 无需改动。
- `UploadModal` 中客户端 canvas 生成缩略图的逻辑（`prepareImage` 内 thumbnail 生成）移除，改为仅计算 SHA-256、尺寸与预览 URL；缩略图统一交由服务端生成（见 10 决策记录）。

## 6. 删除与恢复语义

| 操作 | 存储服务 | D1 |
| --- | --- | --- |
| 从项目移除 | 不操作 | 删除 `project_assets` 行 |
| 软删除（全局回收站） | 不删除文件 | 置 `deleted_at` |
| 恢复 | 不操作 | 清空 `deleted_at` |
| 彻底删除 | `DELETE /v1/blobs/:id`（原图 + 缩略图） | 删除 `assets` 行 |

相比 ResourceSpace 的「回收站 → 彻底删」两步文件操作，本方案把「是否销毁文件」简化为唯一由「彻底删除」触发的动作，软删/恢复完全不触碰文件，逻辑更简单、可逆性更强。

## 7. 部署

### 7.1 连通方式（按配置切换，无需改代码）

- 存储服务以独立 Node 进程运行，监听端口（默认 `18082`），数据目录为本地卷。
- **同一台机器 / 局域网**：Worker 通过本机地址（如 `http://localhost:18082`）访问，无需公网地址与令牌。
- **云端（不同机器）**：存储服务暴露公网 HTTPS 地址，Worker 携带 Bearer Token 访问；令牌只存于服务端，不发往浏览器。
- 两种方式仅改 `IMAGE_STORE_BASE_URL` 与 `IMAGE_STORE_TOKEN` 配置，调用方代码一致。

### 7.2 云端部署

- 存储服务打包为单容器（约十余行 Dockerfile，`node:22-alpine`），挂载一个持久化卷。
- 可部署到 Fly.io / Railway / Render / 任意 VPS；Worker 侧配置 `IMAGE_STORE_BASE_URL` 与 `IMAGE_STORE_TOKEN` 即完成接入。
- 提供 `infra/imagestore/`：`Dockerfile`、`docker-compose.yaml`、`.env.example`，与脚本 `scripts/validation/imagestore/`。

### 7.3 配置项

| 变量 | 含义 | 默认 |
| --- | --- | --- |
| `IMAGE_STORE_ROOT` | 文件数据目录 | `<CWD>/data` |
| `IMAGE_STORE_TOKEN` | 访问令牌（必填） | 无 |
| `IMAGE_STORE_PORT` | 监听端口 | `18082` |
| `IMAGE_STORE_THUMB_MAX` | 缩略图最长边 | `900` |
| `IMAGE_STORE_BASE_URL`（Worker 侧） | 存储服务地址 | 无 |

## 8. 存量数据迁移

> 已确认：存量素材均为示例素材，采用**一次性迁移脚本**迁入；迁移失败可接受，不影响验收。

- 种子素材使用外链 `thumbnail_url`（picsum），无 `storage_key`/`thumbnail_key`，**不受影响，无需迁移**。
- 历史上传到 ResourceSpace 的素材（`external_id` 非空、`storage_key` 为空）在切换后无法取图。切流前用一次性脚本从 ResourceSpace 逐条下载原图与缩略图，写入存储服务并回填 `storage_key`/`thumbnail_key`，随后清空 `external_id`。
- 迁移脚本作为独立工具随仓库提供，运行一次即可；单条失败跳过并记录，不阻塞整体迁移。

## 9. 验证要求

以可重复脚本（`scripts/validation/imagestore/`）验证，结果写入 `validation-results/imagestore/`：

1. 上传 JPEG/PNG/WebP → 返回 blob 元数据，磁盘存在 `blobs/<id>` 与 `thumbs/<id>`，SHA-256 与 `sha256sum` 一致。
2. 缩略图为 WebP、最长边 ≤ 900、宽高比正确。
3. `GET /v1/blobs/:id` 与 `/thumbnail` 返回正确 content-type/content-length/etag/cache-control。
4. 完全重复文件 A/B 被 D1 重复检查识别，C（重新导出）不识别；引用已有素材与仍上传新素材两条分支可用。
5. 软删除后文件仍在磁盘、素材从列表隐藏；恢复后重新可见且可读。
6. 彻底删除后磁盘上原图与缩略图被移除，D1 记录删除。
7. 模拟 DB 写入失败 → 存储服务中的孤儿 blob 被补偿删除。
8. 重启存储服务与 Worker 后，原图、缩略图、元数据均可读（持久化卷生效）。
9. 全仓检查：`grep -ri resourcespace` 与 `RS_` 仅出现在本文档与迁移说明中，代码、配置、依赖中不存在残留。
10. `npm run build` 与现有自动测试通过。
