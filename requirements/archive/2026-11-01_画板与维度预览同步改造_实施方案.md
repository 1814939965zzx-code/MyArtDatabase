## 2. 参照对象：Figma / Linear 到底怎么同步

### 2.1 五个动作（这就是我们要照搬的全部）

用大白话说，Figma 把画板同步当成"**每个人手里的草稿本 + 一块公告板**"：

1. **本地草稿本是唯一真相**。你拖了一下，改的是自己手里的草稿本，立刻生效。网络只决定"别人多久看到"，不决定"你自己看到什么"。
2. **只寄改动，不寄整本**。你拖了一张图，寄出去的是"这张图现在在 (120, 340)"这么一条，不是整个画板。
3. **公告板给每条改动编号**。服务器（公告板）按到达顺序给每条改动编号，再转发给其他人。
4. **自己的改动永远排在最上面**。收到别人的改动或一整份快照时，只合并"自己没在改的部分"；自己正在改的，谁都别动（这叫 rebase）。
5. **旧包直接扔掉**。收到的编号比自己已知的还旧，说明是迟到的包，丢掉不用。

官方依据：Figma《Making multiplayer more reliable》讲了"权威 multiplayer 服务 + WebSocket + checkpoint/journal"这套结构：<https://www.figma.com/blog/making-multiplayer-more-reliable/>；Linear 的公开演讲《Scaling the Linear Sync Engine》讲了"本地库 + 变更队列 + 服务端增量"：<https://linear.app/now/scaling-the-linear-sync-engine>。

**维度预览的坐标是同一套模型的更简单版本**：一个"素材 + 维度"就是一个格子，改了哪个格子只寄哪个格子的新值。

### 2.2 照搬什么、不照搬什么

| 机制 | 是否照搬 | 原因 |
| --- | --- | --- |
| 本地立即生效（乐观更新） | ✅ 照搬 | 这是"跟手"的唯一来源 |
| 只传改动 + 批量合并 | ✅ 照搬 | 把 N 次往返压成 1 次 |
| 服务端给的版本号 + 丢弃旧包 | ✅ 照搬 | 现在画板有雏形但用法错了；预览则完全没有 |
| 未确认的本地改动优先（rebase） | ✅ 照搬 | 这是"不回跳"的根本 |
| 客户端本地缓存 + 断线重试 | ✅ 照搬（用 localStorage 起步） | 弱网/刷新不丢 |
| **实时推送**（Figma 的 WebSocket 广播） | ❌ 不做 | 一人使用、别人偶尔看：打开时拉最新 + 停留低频兜底就够；SSE/WS 都不加（理由见 §10） |
| **增量同步**（`since` 差分） | ❌ 不做 | 全量数据量不大（画板几百条、预览上千条整数），低频拉取足够；没有实时就不需要差分 |
| CRDT（Yjs / Automerge） | ❌ 不做 | 冲突接受"最后写入"，代价高一个量级 |
| 服务端内存态 + journal | ❌ 不做 | 我们每次写直接进 SQLite，已经比 journal 更稳 |

### 2.3 术语对照

| 英文术语 | 我们怎么说 | 在本仓库对应什么 |
| --- | --- | --- |
| optimistic update | 本地先改、后台再存 | `setItems()` / `setPreviewPage()` 立即生效 |
| outbox / mutation queue | 待上传队列 | 新增的 `app/src/sync/outbox.ts` |
| dirty set | 未同步集合 | 记录"哪些键还没被服务器确认" |
| key | 同步最小单位 | 画板=元素 id（Frame 整体算一个键）；预览=`素材id + 维度id` |
| batch / coalesce | 合并成一次提交 | 两个批量接口（画板元素、预览坐标） |
| insert / update / delete | 插入、更新、删除 | 画板批量接口里的 `op`，决定"会不会把已删元素复活" |
| server revision | 服务器版本号 | 画板的 `canvases.revision`；预览新增 `preview_pages.revision` |
| rebase / merge | 快照合并 | 只覆盖"非未同步"的键 |
| local draft | 本地草稿 | `localStorage` 里的未同步副本 |
| delta / since / SSE / tombstone | 增量、实时、墓碑 | **本轮不做**，仅作备选记录见 §13 |

## 3. 现状：两处"跳"的成因

### 3.1 画板：一次拖动的完整时序（RTT≈400ms，选中 6 张图）

```
t=0     按下           → 本地锁定起点
t=0~900 拖动           → 只改本地，顺滑 ✓（这段本来就是对的）
t=900   定时器触发      → 因为"正在拖动"而跳过 ✓
t=1200  松手           → 开始逐条上传：6 次往返 ≈ 2.4 秒
t=1250  定时器又触发    → "正在拖动"已为假，且没检查"正在上传"
                        → 发出一次「整板快照」请求
t=1650  快照回来了      → 服务器这时只存了第 1 个元素
                        → 但它的版本号比本地"新"，被当成最新
                        → 本地整体替换 = 5 张图跳回原位   ← 肉眼可见的回跳
t=3600  6 条上传完成    → 只更新版本号，不修本地元素
t=4500  下一次快照      → 整体替换 = 5 张图跳回终点     ← 第二次回跳
```

**要解决的就是 t≈1650 和 t≈4500 这两次回跳。**

### 3.2 画板根因清单

| # | 根因 | 位置 | 后果 |
| --- | --- | --- | --- |
| R1 | 同步方式是"整板快照替换" | `BoardView.tsx:301-306` | 任何一次快照都会抹掉本地正在进行的改动 |
| R2 | "正在拖动吗"只在**发请求时**判断，**回包时**不复判 | `BoardView.tsx:381-387` | 空闲时发出的请求，会落在用户按下之后 |
| R3 | 判断条件里没有"正在上传" | 同上（有 6 个条件，缺 `savingRef`） | 上传窗口内快照必进，且是半保存状态 |
| R4 | 版本号要等**全部**元素存完才写回本地 | `BoardView.tsx:926-933` | 上传期间本地版本"落后"，唯一的防线失效 |
| R5 | 保存是"每个元素一次请求" | 5 处循环：`648` `666` `930` `1188` `1324` | 8 个元素 = 8 次往返，窗口拉长到秒级 |
| R6 | 失败即整板重载 | `BoardView.tsx:934-937` | 一次超时 = 刚摆好的位置全部退回 |
| R7 | 版本号用当前时间戳生成 | `routes.js:794-798` | 同毫秒两次写入相等，大小比较会漏判 |

### 3.3 维度预览：链路更短，但同样会跳

#### 3.3.1 现在有四条写路径

| 路径 | 触发 | 落库内容 | 位置 |
| --- | --- | --- | --- |
| 场景内拖动图片 | 1D/2D 松手 | `onUpdateAssetDimensions(assetId, 变化的维度)` | `DimensionPreview.tsx:1374-1405` |
| 展开平面拖动卡片 | 1D/2D 松手 | 同上 | `DimensionPreview.tsx:1215-1240` |
| 抽屉里的维度滑块 | 松手 / 失焦 | `onSaveValue(assetId, 单个维度, 值)` | `ArtDatabaseApp.tsx:518-530`、`DimensionControlsEditor.tsx:53-55` |
| 撤销 | `Ctrl+Z` | `onUpdateAssetDimensions(assetId, 撤销快照)` | `DimensionPreview.tsx:800-812` |

四条路径最终都走 `savePreviewDimensionValues`（`ArtDatabaseApp.tsx:557-577`）：先乐观合并进 `previewPage`，再 `PATCH /api/preview-values`，**失败则 `setPreviewRevision(v+1)` 触发整页重取**。

#### 3.3.2 一次连续拖动的时序

```
t=0    拖到 A（松手）       → 本地乐观更新为 A，发出 PATCH#1（慢，2s）
t=800  又拖到 B（松手）     → 本地更新为 B，发出 PATCH#2（快，300ms）
t=1100 PATCH#2 到达服务器    → 数据库 = B
t=2000 PATCH#1 到达服务器    → 数据库 = A（旧值覆盖新值！）
t=2001 页面显示仍是 B        → 本地 B、服务器 A，两者已经分叉
下次刷新/切页                → 图片跳到 A                 ← 回跳
```

再叠加"失败即整页重取"：

```
保存超时 → setPreviewRevision++ → DimensionPages 重取整页
        → previewPage 换成服务器旧值 → 图片跳回旧位置（且 overrides 已清空）
```

#### 3.3.3 预览根因清单

| # | 根因 | 位置 | 后果 |
| --- | --- | --- | --- |
| P1 | 写入接口**没有任何版本号**，只回 `{ok:true}` | `preview-pages.js:179-188`；`preview_pages` 表也没有 revision 列（`:18-25`） | 客户端无法判断回包新旧，无法丢弃过期写入 |
| P2 | 同一坐标的并发写按"到达顺序"落地 | 每键一次 `UPDATE`（`preview-pages.js:185`） | 连续拖动时旧值后到 → 最终坐标是**倒数第二次** |
| P3 | 保存失败即整页重取 | `ArtDatabaseApp.tsx:528`、`:574` → `DimensionPages.tsx:44-63` | 一次超时 = 坐标回退，且覆盖掉本地乐观值 |
| P4 | 每次保存弹一次 toast | `ArtDatabaseApp.tsx:525`、`:570` | 连续拖动刷屏，与"静默同步"相反 |
| P5 | 预览页**完全没有刷新机制** | 全仓库 `setInterval` 只有画板的 900ms 与删除倒计时 | 别人改了坐标你永远看不到，必须手动切页 |
| P6 | 乐观值（`overrides`）与权威值（`previewPage`）两套并存，靠时序巧合对齐 | `DimensionPreview.tsx:192`、`:1235-1239`、`:1400-1404` | 任何一次整页重取都可能让两者错位，出现"松手后先对、再跳回、再跳回来" |

补充一条**不是缺陷但要知道**的事实：预览页一次读取返回整页（最多 1000 个素材 × 若干维度），而 `/api/preview-values` 只写单个素材的若干维度。

## 4. 目标设计

### 4.1 三条铁律（写进代码，也写进测试，不可协商）

1. **本地只增不减**：任何网络回包都不得让用户刚摆放/刚拖动的东西回到旧值。
2. **未同步优先**：合并服务器数据时，只更新"没有未同步改动"的键；有的键一律保留本地值。
3. **旧包必丢**：版本校验发生在**回包时刻**，用请求序号丢弃乱序/过期响应；拿不准就丢弃，宁可不更新也不回退。

### 4.2 数据流（一套内核，三个提交目标）

```
用户操作
  │
  ├─ 本地立即生效：画板 items + frames / 预览 previewPage
  ▼
sync/outbox（共用内核）
  · 按键去重（后写覆盖前写）
  · 空闲 150ms 合并成一批
  · 串行提交 + 退避重试
  · 本地草稿（localStorage）
  · 状态：synced / saving / offline
  │
  ├─ 画板元素（键=元素 id）   → POST  /api/canvas-items/batch
  ├─ 画板 Frame（键=frames）  → PATCH /api/canvases { frames }
  └─ 预览坐标（键=素材+维度） → PATCH /api/preview-values
  │
  ▼
回包 { revision, 归一化后的值, failed[] }
  · 成功键清 dirty、采纳服务器值、记 lastRev
  · not_found → 本地移除并提示一次；其它错误 → 重试
  │
  ▼
拉取（进入页面 / 切回标签 / 窗口聚焦 / 停留 30s，且"无未同步"时才应用）
  · 画板：GET /api/canvas（含 frames、revision、每个元素的 lastRev）
  · 预览：GET /api/preview-page（含 revision、每个坐标的 valueRevs）
```

### 4.3 同步状态与界面表现

**同一个组件 `app/src/ui/SyncStatusDot.tsx`，两处摆放**：画板右下角浮动工具条左侧；维度预览场景右下角、缩放控件左侧。

| 已保存 `synced` | `#9CA3AF` 灰 | 无 | 已保存 | 队列为空且没有失败 |

### 4.4 数据模型变更（全部是加法，可回滚）

| # | 变更 | 作用 | 阶段 |
| --- | --- | --- | --- |
| 1 | `canvases.revision` 改为单调自增 | 版本号语义固定，可比较 | P0 |
| 2 | `canvas_items` 加 `last_rev INTEGER NOT NULL DEFAULT 0` | 记录元素最后一次写入时的画板版本，用于合并 | P1 |
| 3 | `canvases` 加 `frames TEXT` | Frame 从浏览器搬到服务器（JSON 数组） | P1 |
| 4 | `preview_pages` 加 `revision INTEGER NOT NULL DEFAULT 0` | 预览页版本号 | P1 |
| 5 | `preview_dimension_values` 加 `last_rev INTEGER NOT NULL DEFAULT 0` | 每个坐标最后一次写入的版本 | P1 |

迁移写法沿用仓库已有模式（`app/server/db.js:244-248` 的 `PRAGMA table_info` 判断后 `ALTER TABLE ADD COLUMN`），放在现有迁移函数里，可重复执行；旧值从 0 开始，首轮全量拉取时自然对齐。

`revision` 改自增后，现网旧值（13 位时间戳）继续自增仍单调，**不需要数据迁移**；客户端只做大小比较，不解释数值含义。

`canvases.frames` 的内容固定为数组：`[{ "id", "name", "x", "y", "width", "height" }]`，最多 200 个；读不到或解析失败时按空数组处理。

### 4.5 接口契约

> 原则：**只加不改**。原有 `GET/POST/PATCH/DELETE /api/canvas*`、`/api/preview-page*`、`/api/preview-values` 全部保留原样，旧客户端不受影响。

#### 4.5.1 画板：新增批量提交（P0 核心）

一次请求里可以混合三种操作：**插入**（客户端生成 id 的新元素）、**更新**（已存在的元素）、**删除**。这样离线时新画一个矩形、新拖一张图进来也能排队补传。

```
POST /api/canvas-items/batch
Content-Type: application/json

{
  "canvasId": "c_123",
  "ops": [                                   // 最多 200 条
    { "op": "insert", "item": { "id": "cli-6f3a…", "type": "image", "assetId": "a_1",
        "x": 120, "y": 340, "width": 220, "height": 170, "zIndex": 3, "rotation": 0,
        "parentFrameId": null, "payload": null } },
    { "op": "update", "item": { "id": "i_1", "x": 130, "y": 350, "width": 220, "height": 170,
        "zIndex": 3, "rotation": 0, "parentFrameId": null, "payload": null } },
    { "op": "delete", "id": "i_9" }
  ]
}
```

响应：

```json
{
  "revision": 8817,
  "items": [ { "id": "i_1", "…": "服务器归一化后的完整对象", "lastRev": 8817 } ],
  "deleted": ["i_9"],
  "failed": [ { "id": "i_7", "reason": "not_found" } ]
}
```

语义：

1. 校验画板存在，不存在返回 `404 {"error":"画板不存在"}`。
2. **一个 SQLite 事务**内按 `insert → update → delete` 的顺序逐条执行，互不影响。
3. `insert`：`id` 非空且 ≤80 字符；`id` 已存在 → `failed`（`reason:"already_exists"`），**不覆盖**；插入成功 `last_rev = 新版本`。
4. `update`：`UPDATE … WHERE id=? AND canvas_id=?`；`changes=0` → `failed`（`reason:"not_found"`），客户端据此清掉本地这条（说明别处删了）。**绝不会用 update 把已删除的元素复活**。
5. `delete`：不存在也算成功（幂等），回传到 `deleted`。
6. 有任何成功写入才 `bumpRevision` **一次**（整批共用同一个 `revision`）。
7. 回传服务器归一化后的对象（坐标取整、`zIndex` 上限 10000 等），客户端直接采纳——顺带修掉现在"服务端静默裁剪、本地不知道"的分歧。
8. 参数上限：`ops.length ≤ 200`，超出返回 `400`。
9. 图片元素的 `assetId` 不在本项目时记为 `failed`，`reason:"asset_not_in_project"`。

> 为什么不干脆"有则更新、无则插入"：那样一个迟到的 update 会把别处已经删掉的元素重新插回来（数据复活）。显式 `op` 让"更新"永远只更新，"插入"只发生在本地从未确认过的新元素上。

#### 4.5.2 画板：Frame 上服务端（P1）

```
PATCH /api/canvases
{ "id": "c_123", "frames": [ { "id": "frame-c_123-1", "name": "Frame 1", "x": 0, "y": 0, "width": 1200, "height": 900 } ] }
```

响应：

```json
{ "canvas": { "id": "c_123", "frames": [ … ] } }
```

语义：

1. **整体替换**（不做逐个 Frame 的合并）：数组就是这一刻的全部 Frame；空数组表示没有 Frame。
2. 校验：必须是数组、最多 200 个；每个 `id` 非空字符串、`name` 最长 80 字、`x/y/width/height` 为有限数字；不合法返回 `400`。
3. **不 bump `canvases.revision`**：Frame 不是画板元素，让它参与元素版本会让合并逻辑无谓地"变新"。跨端一致性靠"进入页面/切回标签时拉取"，不靠版本号。
4. 读取：`GET /api/canvas` 的 `canvas` 对象里新增 `frames`（解析失败或为空时返回 `[]`）；`GET /api/canvases` 列表不返回（避免列表变重）。
5. 冲突：后写的整份数组覆盖先写的（这就是 §10 决策 2 的"最后写入赢"，Frame 层面按整组算一个键）。

#### 4.5.3 预览：批量提交（P1 核心）

```
PATCH /api/preview-values
Content-Type: application/json

{
  "projectId": "p_1",
  "pageId": "pg_1",
  "updates": [                                   // 最多 200 条
    { "assetId": "a_1", "values": { "d_1": 800, "d_2": 420 } }
  ]
}
```

响应：

```json
{
  "revision": 42,
  "updates": [ { "assetId": "a_1", "values": [ { "dimensionId": "d_1", "value": 800, "lastRev": 42 } ] } ],
  "failed": [ { "assetId": "a_2", "reason": "not_in_page" } ]
}
```

语义：

1. **兼容旧请求**：body 仍是 `{ assetId, values }` 时按单条处理，响应仍含 `ok:true`（旧客户端不会坏）。
2. 一个事务内逐键 `UPDATE preview_dimension_values SET value=?, last_rev=?`；`changes=0`（素材不在 Page / 维度不存在 / 值已被删）记入 `failed`，`reason` 为 `not_in_page` / `dimension_not_in_page`。
3. 有任何成功写入才把 `preview_pages.revision` +1，整批共用同一版本。
4. 值域校验沿用现有规则：必须是 `0~1000` 的整数（`preview-pages.js:181`）。

#### 4.5.4 预览：读取带版本（P1）

`GET /api/preview-page` 在现有 `page` 上新增两个字段（其余不变）：

```json
{
  "page": {
    "id": "pg_1", "projectId": "p_1", "name": "Page 1",
    "selectedIds": ["d_1"], "dimensions": [ … ],
    "assets": [ { "assetId": "a_1", "dimensionValues": { "d_1": 800 }, "valueRevs": { "d_1": 42 } } ],
    "revision": 42
  }
}
```

`valueRevs` 与 `dimensionValues` 一一对应，用于判断"服务器这条比本地新吗"。

#### 4.5.5 拉取与刷新的公共约定

三个读取接口（`GET /api/canvas`、`GET /api/canvases`、`GET /api/preview-page`）都不做差分，规则统一：

| 时机 | 行为 |
| --- | --- |
| 首次进入画板 / 预览页 | 全量拉取一次 |
| 浏览器标签从后台切回（`visibilitychange` → visible）、窗口重新获得焦点（`focus`） | 拉取一次 |
| 停留在页面上且**无未同步改动** | 每 30 秒拉取一次（兜底） |
| 有未同步改动 | 不覆盖本地；等队列清空后再拉 |
| 正在拖动 / 正在保存 | 不发请求；回包到达时也丢弃（铁律 3） |

请求必须带序号（`fetchSeq`），`await` 之后序号过期就丢弃——这同时解决"两个请求乱序返回"的问题。

### 4.6 客户端结构

**新增 `app/src/sync/outbox.ts`**（纯逻辑，可单测）：通用"待上传队列"。

| 导出 | 职责 |
| --- | --- |
| `createOutbox({ submit, batchSize, onStatus })` | 创建队列：`pending`（Map<key, patch>）、`status`、`retryTimer` |
| `set(key, value, { insert })` | 入队/覆盖同键（后写覆盖前写，继承未确认的 `insert` 标记），调度 150ms 后合并提交 |
| `remove(key)` | 入队删除；若该键是未确认的新元素，则直接丢弃队列项 |
| `flush()` | 立即提交（切页、撤销、卸载前） |
| `hasPending()` / `pendingCount()` | 供拉取与合并判断 |
| `retryNow()` | 红点点击 |
| `saveDraft()/loadDraft()` | localStorage 草稿（带版本号） |

关键实现约束：

- **串行提交**：一次只发一批，避免乱序；提交期间新改动只入队。
- **按键去重**：同一键在同一帧内多次改动只保留最后值。
- **按目标接口分流**：同一批里如果同时有"元素操作"和"Frame 操作"，拆成两次请求（先元素批 `POST /api/canvas-items/batch`，再 `PATCH /api/canvases`），不能混在一个请求里。
- **新元素标记为 insert**：本地新建（拖入图片、画矩形/手绘、新建文本）用客户端生成的 id，入队时记 `op:"insert"`；从服务器拉回来的元素一律 `op:"update"`。这条决定"更新会不会把别处删掉的东西复活"。
- **失败分类**：`not_found` / `not_in_page` / `dimension_not_in_page` → 不重试，通知上层清理本地；`already_exists` → 视为已保存（清 dirty）；`401` → 交给 `notifyUnauthorized()`；其它 → 指数退避 1/2/4/8/16s，5 次后转红点，之后每 30s 再试。
- **草稿**：`localStorage["artdatabase:sync-draft:v1:<scope>"]`，`scope` 形如 `canvas:<id>` 或 `preview:<pageId>`；内容 `{ rev, ops }`（含 insert/update/delete 三类）。

**新增 `app/src/sync/id.ts`**：`newSyncId()` —— 优先 `crypto.randomUUID()`；不可用时（局域网 `http://` 不是安全上下文，取不到 `crypto.randomUUID`）退回 `Date.now().toString(36) + Math.random().toString(36).slice(2, 10)`。服务端 `cleanId` 只做去空格与截断 80 字符（`routes.js:63-65`），两种格式都能接受。

**新增 `app/src/sync/canvas.ts`**（画板适配器）：

- 元素键 = 元素 id；Frame 用固定键 `frames`，值 = 整个 Frame 数组；
- `submit` 把队列按 §4.5.1（元素）与 §4.5.2（Frame）分流；
- `merge(items, frames, rev)`：**按全量快照语义处理**——
  1. dirty 键（含待删除的 id）一律保留本地，不被快照覆盖或复活；
  2. 非 dirty 且（本地没有这条 或 `serverItem.lastRev > local.lastRev`）→ 采纳服务器值；
  3. 本地有、快照里**完全没有** → 说明别处删了，本地删除（这与"素材被软删除后 `GET /api/canvas` 不再返回该元素"的现有行为一致）；
  4. Frame 只在没有未同步 Frame 改动时整体采纳服务端数组。

**新增 `app/src/sync/dimensions.ts`**（预览适配器）：键 = `assetId|dimensionId`；`submit` 把按键分组成 §4.5.3 的 `updates`；`merge(page)`：dirty 键保留本地；非 dirty 且（本地没有这个坐标 或 `serverRev > localRev`）→ 采纳服务器值；坐标不在 `page.assets` 里或维度不在 `dimensions` 里 → 本地删除。

**两个 hook**：`app/src/useBoardSync.ts`、`app/src/useDimensionSync.ts`，把队列包成 React state，暴露 `{ items, frames, status, retry, commit, merge, flush }`。

**新增 `app/src/ui/SyncStatusDot.tsx`**：§4.3 的圆点，两处复用。

**归属约定**：

- 画板：`BoardView` 内部自建同步器（当前它自己管全部状态）。
- 预览：`ArtDatabaseApp` 创建（它已持有 `previewPage` 与保存入口），把 `status`/`retry` 透传 `DimensionPages` → `DimensionPreview` 显示；**`DimensionPages` 拉到的新 `page` 必须交给 App 的合并入口**（新增 prop `onReceivePage(page)`，App 里调 `dimSync.merge(page)` 后 `setPreviewPage`），不能直接 `onPageChange(result.page)`（现在就是这么写的，`DimensionPages.tsx:57`，会绕开未同步保护）。

### 4.7 冲突与失败策略（决策表）

| 情况 | 处理 | 用户看到 |
| --- | --- | --- |
| 两人同时改**不同**元素/坐标 | 各存各的，互不影响 | 无感 |
| 两人同时改**同一**元素/坐标 | 后到服务器的赢（LWW）；输的一方在下一次拉取时变成对方的值 | 值变到对方位置，无提示（这就是 §10 决策 2） |
| 两人同时改 Frame | 整份 Frame 数组后写覆盖先写 | 后改的人看到的框留下来 |
| 我拖的元素被对方删了 | 批量返回 `not_found` → 本地移除 | 提示一次"有元素已在其他窗口被删除" |
| 我改的坐标所在素材被移出 Page | `not_in_page` → 本地移除该素材的坐标 | 提示一次 |
| 维度被删 | `dimension_not_in_page` → 本地丢弃该维度所有值 | 无感（维度已不在列表里） |
| 画板 / Page 被对方删了 | 404 → 停止队列、锁定红点 | 提示并返回主页 |
| 网络中断 | 指数退避重试，5 次后转红点并每 30s 再试 | 红点，可点重试 |
| 登录过期（401） | 沿用现有 `notifyUnauthorized()` | 弹出登录 |
| 单批超过 200 项 | 客户端按 100 个一批切片提交 | 无感 |
| 服务器归一化与本地不同（如 zIndex 被裁剪、坐标取整） | 采纳服务器值 | 无感 |
| 文本连续输入 / 滑块拖动 | 300ms 空闲才入队；松手即入队 | 无感 |
| 离线时新建元素（拖入图片、画形状、新建文本） | 客户端生成 id，`op:"insert"` 入队，恢复后补传 | 立刻出现在画板上，红点提示未同步 |
| 我刚删了元素，但快照里还有它 | 删除也在 dirty 里，快照不复活 | 无感 |
| 我的 update 迟到，元素已在别处被删 | 服务器返回 `not_found` → 本地移除，**不复活** | 提示一次"有元素已在其他窗口被删除" |
| 离线时做"结构操作"（新建 Page、把素材加入 Page、新建/重命名维度、上传素材、重命名项目） | **不在本轮范围**：仍走原接口，失败照旧提示 | 明确的错误提示，不会假装成功 |

### 4.8 离线能力边界（写清楚，避免"看起来能存其实不能"）

| 操作 | 离线时 | 恢复网络后 |
| --- | --- | --- |
| 画板：移动/缩放/置顶置底/删除元素、新建/移动/缩放/重命名/删除 Frame、画形状/手绘、新建文本、编辑文本 | ✅ 可编辑 | 自动补传 |
| 画板：从素材托盘拖入图片 | ✅ 可编辑（`insert`） | 自动补传 |
| 画板：新建/删除 Page | ❌ 仍走原接口，失败提示 | 需要重新操作 |
| 维度预览：拖动图片、拖滑块、撤销 | ✅ 可编辑 | 自动补传 |
| 维度预览：把素材加入 Page、新建维度、改维度名称、删除维度 | ❌ 仍走原接口，失败提示 | 需要重新操作 |
| 上传素材、素材详情编辑、标签编辑 | ❌ 不受本次改造影响（原本就不支持离线） | — |

判断标准：**只改已有数据或"画板内元素"的，离线可编辑；改"页面/项目结构"的，离线不承诺。**

## 5. 分期实施

> 两块同步推进：**P0 先把两个界面一起止血**（上线后用户立即能感知"不跳了"），P1 再抽共用内核并把 Frame 搬上服务器。

### 5.1 P0：止血（画板 + 预览）

**画板**

1. `loadCanvas` 加请求序号（`fetchSeq`），`await` 之后序号不符直接丢弃。
2. `await` 之后**再判一次**：拖动中、平移中、绘制中、`savingRef > 0`、有 dirty，任一为真就放弃本次快照。
3. 轮询条件补 `savingRef.current === 0`。
4. 新增批量接口（§4.5.1），把 5 处逐条循环改成一次调用。
5. 失败不再 `loadCanvas()` 回滚，改为保留本地 + 记录失败（P0 用 toast 兜底，P1 换红点）。
6. `revision` 改为自增。

**维度预览**

### 6.4 `app/src/sync/outbox.ts`（新增）

按 §4.6 实现。必须满足：

- `set(key, value, { insert })` 同键覆盖、`remove(key)` 记删除；`insert` 只对"本地新生成、服务器还没确认"的元素为真；
- **`insert` 标记随键保留**：尚未确认的新元素又被拖动/改了文字，后续 `set` 必须继承 `insert` 标记（否则会被当成 `update`，服务端 `not_found`）；
- **新建后未确认就被删**：直接把队列项丢掉，不发 `delete`（服务器根本没有这条）；
- 同一队列可能同时有元素改动与 Frame 改动：**按目标接口分流成两次串行请求**（元素批 → Frame）；
- 提交串行、单批 ≤100 项；
- `flush()` 返回 Promise（撤销/切页要等它）；
- 失败分类见 §4.7（`not_found` 清理本地、`already_exists` 视为已保存、`401` 交给 `notifyUnauthorized()`、其它退避重试）；
- 草稿读写（含 `insert`/`update`/`delete` 三类）与 `status` 订阅（`subscribe(fn)` 返回取消函数）。

### 6.5 `app/src/sync/canvas.ts` + `app/src/useBoardSync.ts`（新增）

- 元素键 = 元素 id，`submit` → `POST /api/canvas-items/batch`（带 `op`）；

### 7.2 手工验收（你自己就能做，不需要写代码）

**画板**

1. 打开画板，按 `F12` → `Network` 面板 → `Throttling` 选 `Custom`：Latency **400 ms**、Download/Upload **400 kbps**。
2. 框选 5~8 张图，连续拖动，**每次松手后 1 秒内立刻再拖**，重复 20 次。✅ 通过 = 始终跟在鼠标下、松手即最终位置、一次不回跳。
3. 看网络面板：一次多选拖动只应出现 **1 个** `batch` 请求。
4. 拖动一个 Frame 松手，再拖动它里面的图片：Frame 与图片都不回跳；网络面板里 Frame 只有 1 个 `PATCH /api/canvases`。
5. `Network` 切 `Offline`：拖动 3 次、改一次文本、移动一次 Frame。应显示红点、编辑不丢；切回 `Online` 后几秒内变灰，刷新仍在。
6. 再刷新一次：位置、文本、Frame 都在。
7. **Frame 跨设备**：复制当前地址到另一个浏览器（或隐身窗口）打开同一个画板，Frame 的名字/位置/尺寸应与刚才一致；清掉该站点的 `localStorage` 再刷新，Frame 仍在。
8. **别人看一眼**：另开一个窗口打开同一画板（模拟"偶尔打开看"），应立刻看到最新内容；让编辑窗口拖动后，把查看窗口切走再切回（或等 30 秒），应看到最新位置。**不要求秒级实时。**
9. **离线新建**：切 `Offline`，从托盘拖一张图进画板、用矩形工具画一个框、双击写一行字。三样都应立刻出现在画板上；切回 `Online` 后几秒内红点变灰，刷新页面三样都还在（这是"客户端生成 id"验得对不对的关键一步）。
10. **离线时的边界**：切 `Offline` 后新建一个 Page，应给出失败提示（不假装成功）——这是本轮明确不承诺的部分。
11. **删除不会复活**：A 窗口删掉一张图，B 窗口（之前打开过）等 30 秒或切回标签后，这张图应消失而不是重新出现。

**维度预览**

12. 选 1D 或 2D（3D 本来就不让拖），把同一张图连续快速拖 5 次，每次松手间隔 <0.5 秒。
    - ✅ 通过：图片始终停在鼠标下；**等 5 秒后刷新页面，位置仍是最后一次**（不是倒数第二次）。
13. 把网络切成 `Offline`，拖 3 次，再切回 `Online`：红点应在几秒内变灰，刷新后坐标正确。
14. 拖动过程中观察：不应再出现"维度位置已保存"的 toast；只有角落里的小圆点变化。
15. 打开素材详情抽屉，拖维度滑块后松手：不回跳、不弹提示；关掉抽屉再打开，值仍在。

## 8. 风险、回滚与兼容

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 版本号语义变化（画板） | 若某处代码假设它是时间戳 | 全仓库只有 4 处比较大小，统一"只比大小"；不参与任何时间判断 |
| Frame 整组覆盖 | 两人同时改 Frame 会互相覆盖 | 已接受（§10 决策 2）；Frame 是低频操作，且本产品以单人编辑为主 |
| 老用户的本地 Frame | 迁上服务器后若处理不当会"凭空消失" | 首次加载做一次性迁移（§5.2 第 11 条），用 `localStorage` 标记防重复；服务端为空才迁移，不覆盖服务端已有数据；每次加载成功都写标记 |
| 客户端生成 id | 两处代码可能各造一套 id 规则 | 统一走 `sync/id.ts`；服务端 `cleanId` 只做 trim + 截断，兼容 uuid 与 `时间戳+随机串`；`insert` 遇到已存在 id 不覆盖 |
| 全量快照的删除语义 | "快照里没有"被误判成"删了" | 只有**非 dirty** 的键才按"缺席即删除"；自己正在改/正在删的一律保留。素材被软删除导致元素从快照消失，属预期行为 |
| 迟到的 update 复活已删元素 | 别人删了、我的旧请求后到 | `op:"update"` 命中 0 行即 `not_found`，客户端删本地；插入只发生在 `insert` |
| 预览页数据量大 | 一次全量可能有上千素材 | 只在"无未同步 + 进入/切回/30s"时拉；页面停留在后台时不拉 |
| 滑块高频写 | 拖滑块时每个 pointermove 都发 | 只在松手/失焦入队；队列 150ms 合并 |
| 批量接口部分失败 | 客户端可能反复重试 | 只有 `not_found` / `not_in_page` / `dimension_not_in_page` 不重试（清理本地），网络类错误才重试 |
| 本地草稿与服务端分叉 | 换机器看到旧草稿 | 草稿带 `rev`，启动时若服务端更新则先合并、只补传 dirty 键 |
| 新表/新列 | 老库升级 | 全部 `IF NOT EXISTS` / `PRAGMA` 判断，可重复执行；不删列不改列 |
| 回滚 | 需要回到旧行为 | P0/P1 都是加法：回滚客户端即恢复"整表快照"；新列留着不影响旧代码 |

## 9. 不做什么

- **不做实时推送**（WebSocket / SSE）：一人使用、别人偶尔看，打开时拉最新 + 30s 兜底已够（§10 决策 3）。
- **不做增量同步**（`?since=`）与墓碑表：没有实时就不需要差分；数据量可接受。
- **不做 CRDT**（Yjs/Automerge）：冲突接受"最后写入"，收益只在"两人同时拖同一张图"，代价高一个量级。
- **不把整块画板/整页预览存成一个大 JSON**：改一个坐标要重写全部数据，且没有增量能力可谈。
- **不做"手动保存按钮"**：Figma 式体验的核心就是没有保存按钮。
- **不改画板与预览的交互**：吸附、撤销、框选、Frame 归属、聚堆、象限隔离、3D 禁止拖动，一律不动。
- **不把预览改成"边拖边存"**：仍然是松开后保存（`CURRENT.md:109`），只是保存变成"本地先定稿 + 后台提交"。

| # | 决策 | 落实方式 |

| --- | --- | --- |

## 13. 备选（本轮不实施）：增量同步与实时推送

> 只有在将来变成"两人以上长期同时编辑同一画板/预览页"时才需要。保留设计，避免以后重新调研。

- **触发条件**：出现"必须秒级看到对方改动"的实际需求，或单页数据量涨到全量拉取不可接受（例如预览页 > 5000 素材，或画板 > 3000 元素）。
- **增量**：`GET /api/canvas?since=rev` 只返回 `last_rev > since` 的元素与 `deletedIds`；`GET /api/preview-page?since=rev` 只返回 `valueRevs > since` 的坐标与 `removedAssetIds`。需要两张墓碑表（`canvas_item_tombstones`、`preview_page_asset_tombstones`）记录删除。
- **实时**：SSE（不是 WebSocket）两路频道 `/api/canvas-events?canvasId=`、`/api/preview-events?pageId=`；Node 单进程用 `Map<channel, Set<res>>`，写操作后广播 `{ revision, changedIds }`，25 秒心跳；客户端只在"无未同步"时应用。
- **前提**：先有 P1 的 `last_rev`/`valueRevs` 与合并逻辑；增量与实时都是在这之上的加法，不会推翻 P1。
