# AI 识图自动打标签服务调研

> 调研日期：2026-08-18
> 目标：为 artDatabase 现有图片素材库接入 AI 识图自动打标签能力，优先寻找**不改主程序代码**即可落地的方案。
> 本文档为调研结论，尚未进入产品规则（CURRENT.md 未更新）。

## 1. 背景与目标

当前素材库的全局标签完全依赖用户手工输入（上传时或详情中编辑），团队素材量增长后标注成本高、标注口径不统一。调研目标：

1. 自动识别图片内容（主体、场景、风格、色调、构图等）并生成标签；
2. 把标签写回现有数据库，让现有搜索、标签筛选能力直接生效；
3. 优先不修改主程序代码（外部服务/脚本接入）。

## 2. 现状盘点：可接入点与约束

| 事项 | 现状 | 对 AI 打标签的意义 |
| --- | --- | --- |
| 标签存储 | `assets.tags`，TEXT，逗号分隔；`PATCH /api/assets` 时截断为 **20 个 / 800 字符** | AI 输出需排序、截断；无"AI 来源"字段，AI 标签与人工标签无法区分 |
| 读取原图 | `GET /api/media?id=<assetId>&variant=original`（本地文件 `media/blobs/<storage_key>` 也可直接读） | Sidecar 可通过 HTTP 拿原图，无需碰文件系统 |
| 素材清单 | `GET /api/library` 返回全部未删除素材（含 id、tags、thumbnailUrl、originalUrl、description、notes、sourceUrl） | Sidecar 可直接据此发现"还没有标签"的素材 |
| 写回标签 | `PATCH /api/assets`，body 为 `{ id, name, tags, description, notes, sourceUrl }`，tags **全量覆盖** | Sidecar 必须"读现有字段 → 合并 tags → 整体回写"，否则会覆盖其他字段 |
| 数据库 | SQLite（`node:sqlite`，未开 WAL），单 Node 进程独占写入 | 外部进程直写 SQLite 有并发锁风险，详见 5.2 |
| 网络形态 | 局域网服务，无鉴权 | Sidecar 调用本机 API 无障碍；但上传图片到云 API 等于让素材出内网 |
| 素材类型 | 仅 JPEG / PNG / WebP，单文件 ≤ 50MB | 主流模型 API 均支持这些格式 |

结论：现有 `/api/library` + `/api/media` + `/api/assets` 三个接口已经构成完整的"读图 → 识图 → 写回标签"闭环，**技术上可以做到完全不改主代码**。

## 3. 方案总览

| 方案 | 代表实现 | 效果 | 成本 | 隐私 | 落地难度 |
| --- | --- | --- | --- | --- | --- |
| A. 本地专用标签模型 | WD14 / JoyTag / RAM++ / Florence-2 | 好（英文标签为主） | 免费，需 CPU/GPU 算力 | 不出内网 | 中 |
| B. 本地多模态大模型 | Ollama + Qwen3-VL / Qwen2.5-VL | 好，中文标签、可控输出 | 免费，需 ~8GB+ 内存/显存 | 不出内网 | 低 |
| C. 云视觉 API | 通义 Qwen3-VL、Gemini 2.5 Flash、GLM-4.5V、GPT-4o、百度图像识别 | 最好，中文友好 | 按量计费，图片级约 ¥0.001～0.05/张 | 图片出内网 | 最低 |
| D. 现成 DAM 智能能力 | Immich ML（CLIP 语义搜索） | 提供"免标签检索"，但不写 tags 字段 | 免费 | 不出内网 | 中，需迁移 |
| E. 无代码工作流 | n8n / Dify / Coze 编排云 API | 取决于所接 API | 取决于所接 API | 出内网 | 低，但受平台限制 |

## 4. 详细方案

### 4.1 本地专用标签模型（A）

- **WD14 tagger（wd-swinv2-tagger-v3）**：二次元/插画/设计图打标签的事实标准，输出 Danbooru 风格英文标签（`building, fog, atmosphere, gray scale`）。用 onnxruntime 纯 CPU 约 0.5～2 秒/张，质量稳定、免费。ComfyUI 生态有现成批量节点（[ComfyUI-WD14-Tagger](https://github.com/pythongosssss/ComfyUI-WD14-Tagger)），也有独立 GUI 批量工具（wd14-tagger-standalone）。
- **JoyTag**：Danbooru 标签模型，[JoyTag](https://sd114.wiki/542.html) 精度比 WD14 更高、无审查过滤，小模型 CPU 可跑，适合动漫/插画素材。
- **RAM++ / Tag2Text（recognize-anything）**：通用真实照片的物体/场景/属性标签，英文输出，可配合词典翻译成中文。
- **Florence-2**：微软开源，支持看图说话 + 目标检测，可输出短句描述，适合生成 `description` 字段而非标签。

共性：标签为**英文**，需要维护一张"英文标签 → 中文标签"映射词典（可先人工维护 Top 500 高频词，后续按素材领域扩充）。

### 4.2 本地多模态大模型（B）

- **Ollama + Qwen3-VL / Qwen2.5-VL**：`ollama run qwen3-vl:8b` 一条命令起服务，自带 OpenAI 兼容 HTTP API。7B/8B 量化版可在 8～16GB 内存的普通电脑（甚至 Mac）上 CPU 运行。**中文标签能力强**，可通过 prompt 控制输出格式（如"输出 5～15 个逗号分隔的中文标签"），电商商品图自动标注已有成熟实践（[Qwen2.5-VL+Ollama 商品图标注](https://adg.csdn.net/6a2badca10ee7a33f27ba194.html)、[Ollama 部署 + JSON 导出](https://blog.csdn.net/weixin_36474966/article/details/157745606)）。
- 备选：llava、minicpm-v（更小更快，中文略弱）、Qwen3-VL 2B（内存 <4GB 可跑）。
- 缺点：CPU 推理 3～10 秒/张，批量补打时需要跑一段时间；标签质量略低于云 API。

### 4.3 云视觉 API（C）

| 服务 | 模型/能力 | 中文能力 | 大致成本（每张图，估算，以官网为准） | 备注 |
| --- | --- | --- | --- | --- |
| 阿里云百炼 | Qwen3-VL-Plus / Qwen-VL-Plus | 强 | 约 ¥0.002～0.01 | 国内直连，[计费页](https://help.aliyun.com/zh/model-studio/model-pricing) |
| 智谱 AI | GLM-4.5V | 强 | 有免费额度，超出后约 ¥0.001～0.01 | 国内直连，免费额度适合先验证 |
| Google | Gemini 2.5 Flash | 强 | 约 $0.00003～0.0002（¥0.0002～0.0015） | 便宜；国内直连受限 |
| OpenAI | GPT-4o / GPT-4.1 | 强 | 约 $0.001～0.005 | 最贵 |
| 百度智能云 | 通用物体识别 / 图像标签 API | 中 | 预置接口，按次计费 | 无需写 prompt，标签固定词汇表 |
| Azure / AWS | AI Vision / Rekognition | 中（英文为主） | 按次计费 | 适合已有云账号的团队 |

要点：单张 1024px 图约折合 1000～1600 tokens，输出 10～20 个标签约 100～200 tokens，按此估算 1 万张图的总成本约 **¥10～300**，量级上完全可接受（[价格对比站](https://302.ai/product/detail/qwen3-vl-plus-2025-12-19)、[模型比价](https://devtoolpicks.com/ai-models?page=7)）。

### 4.4 现成 DAM 智能能力（D）与工作流（E）

- **Immich ML**：自带 CLIP 语义搜索（"红衣服的人"直接搜图），但**不写标签字段**，等于另一条"免标签"路线；需要把素材迁到 Immich，成本高，仅作备选。
- **n8n / Dify / Coze**：可编排"定时任务 → 调云 API → 调 `/api/assets` 回写"，适合不想写任何代码的场景；灵活性受平台限制，局域网直连本机 API 通常没问题。

## 5. 集成方式对比（重点：不改主代码）

### 5.1 外部 Sidecar 通过现有 HTTP API 读写（推荐）

一个独立小服务/脚本（Python 或 Node 均可），与本应用并行运行，**只通过 HTTP 与本应用交互**：

```text
① GET  /api/library                     → 素材清单（找出 tags 为空的素材）
② GET  /api/media?id=...&variant=original → 原图字节
③ 调用 AI（本地模型 / Ollama / 云 API）    → 候选标签 + 置信度
④ 规范化：翻译、去同义词、按置信度排序、截断到 20 个
⑤ PATCH /api/assets {id, name, tags, description, notes, sourceUrl}
   → 保留 ① 里读到的现有字段，仅合并 tags
```

优点：

- **零主代码改动**，复用服务端已有校验（标签去空、20 个上限、800 字符）；
- 不碰 SQLite，无并发锁问题；应用重启、改库路径都不影响；
- 天然支持"仅对无标签素材补打"，不会覆盖人工标签（细节见第 6 节合并策略）。

缺点：大批量补打时逐个走 HTTP，10 万张图会有一定耗时（瓶颈在 AI 推理而非 HTTP）。

触发方式三选一：

1. **一次性批量补打**：脚本跑一遍存量素材后退出，最简单；
2. **定时轮询**：cron / systemd timer 每 10 分钟跑一次增量（发现 `createdAt` 新且 tags 为空）；
3. **常驻守护**：监听 `/api/library` 或 blobs 目录，新素材出现即打标（可用 [watchdog](https://pypi.org/project/watchdog/) 监听 `media/blobs/`）。

### 5.2 外部进程直连 SQLite（快，但有风险）

外部脚本直接打开同一个 `.db` 文件：`UPDATE assets SET tags = ? WHERE id = ?`。

优点：批量速度快，一个事务几千行。

风险与缓解：

- **并发写锁**：主进程用 `node:sqlite` 未开 WAL（`app/server/db.js` 未设置 `journal_mode`），外部进程写时可能与主进程写撞出 `SQLITE_BUSY / database is locked`。缓解：一次性执行 `PRAGMA journal_mode=WAL;`（对库文件生效，属于改数据库配置而非改代码）；写入时加 busy_timeout 重试；
- **绕过业务校验**：直接写库不经过 20 个/800 字符截断，需脚本自行复刻规则；
- **绕过并发保护**：`PATCH /api/assets` 的 tags 是整字段覆盖，直写库同样要"先读后合并"，否则与用户同时编辑时互相覆盖。

结论：仅当素材量大、HTTP 回写太慢时才考虑；一般场景 5.1 足够。

### 5.3 前端注入脚本（不推荐）

Tampermonkey 等浏览器脚本在上传页/详情页自动调 AI 填标签。优点是不动任何服务端；缺点是每个使用者都要装插件、依赖浏览器环境、脆弱难维护。仅作个人临时用法。

### 5.4 未来若允许改代码（供决策参考，本次不做）

- 上传流水线内同步/异步打标（`POST /api/uploads` 之后排队打标）；
- `assets` 表新增 `ai_tags`、`tag_confidence`、`tag_status`（待确认/已采纳）等列，把 AI 标签与人工标签分开，支持"一键采纳"；
- 前端增加"AI 打标"按钮与结果确认 UI。

## 6. 关键决策点（无论选哪条路线都需要先定）

| 决策 | 选项 | 建议 |
| --- | --- | --- |
| 标签语言 | 英文（Danbooru 风格）／中文／双语 | 面向中文团队建议**中文**；若用 WD14 需维护翻译词典 |
| 打标范围 | 只打"tags 为空的素材"／全部素材 | 不改代码的前提下建议**只打空标签素材**，避免 AI 覆盖人工标注 |
| 合并策略 | 追加、覆盖、仅补空 | **仅补空**最安全；合并时去重、按置信度排序 |
| 标签数量 | AI 输出往往 >20 个 | 按置信度取 Top 10～20，配合系统 20 个上限截断 |
| 标签粒度 | 主体/场景/风格/色调/构图/用途 | 让 prompt 固定输出类别，保证口径一致 |
| 规范化 | 同义词合并（人/人物/person） | 先跑一批看高频词，再定词典；云大模型可让它"用已有标签库的词汇" |
| 隐私 | 素材是否允许出内网 | 素材含客户/保密内容则必须选本地模型（A/B） |
| 误标处理 | 用户手工删除后 AI 是否重标 | 不改代码时无法记忆"已否决标签"，建议打标后人工抽查，错标手工删 |

## 7. 推荐路线（分阶段）

1. **验证期（1～2 天，零改代码）**
   - 选 100 张有代表性的素材；
   - 若允许出内网：用**智谱 GLM-4.5V 免费额度**或**通义 Qwen3-VL** 打中文标签；
   - 若必须内网：笔记本跑 **Ollama + qwen3-vl:8b**；
   - Sidecar 按 5.1 的 HTTP 闭环写回，人工抽查准确率与标签风格。
2. **小规模推广（1 周）**
   - 按抽查结果调 prompt（标签类别、数量、语气），确定规范化词典；
   - 对存量"无标签素材"批量补打（晚间跑）；
   - 云端则开正式计费（估算成本见 4.3，1 万张量级 <¥300）。
3. **常驻化（可选）**
   - systemd 定时任务/守护进程自动增量打标；
   - 若效果好且愿意改代码，再评估 5.4 的深度集成（AI 标签分区、确认流程）。

**PoC Sidecar 伪代码（Python，约 60 行）：**

```python
import requests
BASE = "http://localhost:3000"

def ai_tag(image_bytes):
    # 例：Ollama 本地
    r = requests.post("http://localhost:11434/api/generate", json={
        "model": "qwen3-vl:8b", "prompt":
        "观察这张图片，输出 8~15 个中文标签，逗号分隔，"
        "只描述主体、场景、风格、色调、构图，不要解释。",
        "images": [image_bytes], "stream": False})
    return r.json()["response"]

assets = requests.get(f"{BASE}/api/library").json()["assets"]
for a in assets:
    if a["tags"]:            # 只处理还没有标签的素材
        continue
    img = requests.get(f"{BASE}{a['originalUrl']}").content
    raw = ai_tag(img)
    tags = normalize(raw)[:20]        # 去重、去空、截断
    if not tags:
        continue
    requests.patch(f"{BASE}/api/assets", json={
        "id": a["id"], "name": a["name"],
        "tags": ",".join(tags), "description": a["description"],
        "notes": a["notes"], "sourceUrl": a["sourceUrl"]})
```

验证清单：

- [ ] 打标前后 `GET /api/library` 中 tags 数量 ≤ 20、无空串；
- [ ] 素材其他字段（name/description/notes/sourceUrl）未被覆盖；
- [ ] 全局搜索与标签筛选能命中新标签；
- [ ] 人工编辑该素材标签后，AI 不再重复覆盖（仅补空策略下天然满足）；
- [ ] 抽 20 张图人工核对标签准确性，输出错标样例。

## 8. 风险提示

- **锁库风险**：除非必要不要用 5.2 直连写库；若用，先开 WAL 并加超时重试。
- **覆盖风险**：`PATCH /api/assets` 是 tags 全量覆盖，Sidecar 必须合并现有 tags（或只处理空标签素材）。
- **标签爆炸**：AI 词汇自由度高，几万张图后标签库会碎片化；建议尽早定"输出类别 + 同义词词典"，或用已有高频标签约束 prompt。
- **图片出内网**：使用云 API 前需团队确认素材保密要求。
- **软删除/恢复**：恢复的素材 tags 仍在，不会被重复打标（tags 非空即跳过）。

### 一句话结论

**不改代码即可接入**：用一个小型外部 Sidecar，通过现有 `GET /api/library`、`GET /api/media`、`PATCH /api/assets` 三个接口完成"读图 → AI 识图 → 写回标签"闭环；模型优先选**中文多模态大模型**（云上通义 Qwen3-VL / 智谱 GLM-4.5V，内网用 Ollama + Qwen3-VL），只对**无标签素材**补打，避免覆盖人工标注。
