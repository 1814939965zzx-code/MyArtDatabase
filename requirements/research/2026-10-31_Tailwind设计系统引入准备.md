# Tailwind 设计系统引入准备清单

> 本文是 2026-10-31 的调研快照，落地计划见 `requirements/archive/`；代码现状与实现细节以 AOCI 认知索引为准。

> 调研日期：2026-10-31
> 范围：`app/` 前端（React 19.2 + Vite 8 + Tailwind CSS v4.2），不含 `extension/`（Chrome 扩展用 Shadow DOM 自带样式）。
> 目的：回答"要把 Tailwind 变成统一控件 / 色值 / 字号的**设计系统**，需要先准备什么"。本文只做盘点与方案，不改代码。

## 1. 结论摘要

1. **Tailwind 不是"还没引入"**：`@tailwindcss/vite` 已接入，`globals.css` 首行 `@import "tailwindcss"`，构建产物里已有 preflight、`@layer` 和 `--tw-*`。真正缺的是设计系统本身——token 层、原语组件层、样式分层和治理规则。这项工作的正名是"把 Tailwind 用起来"，而不是"安装 Tailwind"。
2. **现状是 100% 手写 CSS**：`app/src/globals.css` 单文件 1,124 行，约 939 个规则块、498 个类名；24 个 TSX 共 611 处 `className`，其中约 609 处是自定义类。全仓库没有使用任何 Tailwind utility（构建 CSS 里连 `.flex` 都不存在）。
3. **失控程度可量化**：221 种 hex、61 处 rgba、19 种字号（≤12px 占 205 处）、13 种字重、16 种圆角、28 种 z-index、25 种阴影、14 种过渡时长、151 种 padding/margin 取值。这些既是设计系统要收敛的对象，也是"统一"是否达成的验收指标。
4. **需要准备 7 类东西**：(A) 决策、(B) token 层、(C) 原语组件层、(D) 基础设施、(E) 样式分层与迁移策略、(F) 文档与治理、(G) 验证手段。逐项见 §3，最小可交付见 §6。
5. **最容易踩的坑是层叠顺序**：现有 CSS 未分层，而"未分层样式优先级高于所有 `@layer`"。直接把 utility 加到旧元素上会被旧规则压掉，表现为"类写了没效果"。必须先把旧 CSS 用 `@import "./styles/legacy.css" layer(components)` 降级，否则迁移寸步难行（详见 §5）。
6. **建议"先等价抽取，再统一调整"**：第一版 token 的取值等于现值，迁移后截图应零差异；字号提升、对比度修正、间距取整作为第二批独立评审，因为它们改变信息密度，属于产品决策而非重构。
7. **粗估工作量**（单人）：token + 分层 1~2 人日；5 个高频原语 2~3 人日；8 个视图逐页迁移 4~8 人日；治理与清理 1~2 人日；合计约 2~3 周，可分阶段交付。

## 2. 现状盘点（可复核的代码事实）

### 2.3 重复模式（组件化的直接理由）

- **弹窗**：12 个文件各自手写 `modal-backdrop > modal-card > modal-heading > modal-form > modal-actions`（`modal-backdrop` 在 TSX 中出现 17 次），结构相同但关闭逻辑、尺寸、标题区各写一遍。
- **按钮**：`primary-button` 26 处、`secondary-button` 24 处、`icon-button` 21 处；此外还有 100+ 条以容器限定的专用按钮规则（`.tag-manager-actions button`、`.user-manager-actions button.danger`、`.board-actions > button`、`.annotate-tools button.active`……）。
- **弹层 z 值互不一致**：同一语义的"模态"出现四种层级——`.modal-backdrop` 80、`.dimension-editor-backdrop` 90、`.replacement-backdrop` 100、`.frame-delete-backdrop` 30000；下拉类还有 `user-menu-dropdown` 60、`frame-context-menu` 20000、`asset-tag-suggestions` 3。
- **状态色三套**：`.component-status.success/warning`、`.ai-config-message`、`.form-error`、`.user-manager-message` 各自定义绿/黄/红。
- **动态类名普遍**：100+ 处模板拼接，例如 `handle-${dir}`、`mode-${n}`、`${cond ? "active" : ""}`。Tailwind 的扫描器无法识别拼接结果，`cn()` 也无法合并。

### 2.4 设计资产现状

- `:root` 只有 10 个变量（`globals.css:3-14`），实际却用了 221 个 hex——变量只覆盖了 6 个颜色，其余全部散落在规则里。
- `--font-geist-sans`（`globals.css:24`）与 `--font-geist-mono`（`:211`）**从未定义**，看起来是从别的模板抄来的残留；`body` 实际回落到 `PingFang SC / Microsoft YaHei`，字体选择事实上无人管理。
- 字号重心在 12px（130 处），10px 用于徽标；`CURRENT.md` §3.4 又单独规定坐标气泡 14px——说明字号是逐需求追加的，没有全局约定。
- 对比度实测（WCAG AA 正文要求 4.5:1）：`ink/paper` 14.28 ✓、白字/`sage` 4.91 ✓、`muted/paper` **4.12 ✗**、`muted/surface` **4.39 ✗**、白字/`accent` **3.87 ✗**（12px 主按钮文字不达标）。
- 层级契约其实已经存在，但只写在注释里（`globals.css:467`）：侧栏 30 / 顶栏 20 / 专注层 50 / 抽屉 60 / 弹窗 80 / toast 100。**画板内部 z-index（1000~30000）是元素层序，不是页面层级**，token 化时不能合并。

### 2.5 已有基础（可复用，别推翻重来）

- 已有"视觉组件"页（`VisualComponentsPage.tsx`，224 行），入口在顶部用户菜单（`ArtDatabaseApp.tsx:939`），渲染于 `:961`；它直接复用生产样式，是天然的"设计系统文档页"落点——但目前是手写类，不是 token 驱动。
- 品牌四色（ink / paper / accent / sage）已在 1,000+ 行 CSS 中稳定使用，可直接升格为品牌 token。
- 弹窗、按钮、输入框的 DOM 结构已经收敛（`modal-card`、`modal-form` 等），抽象原语时可沿用现有结构，视觉回归风险较低。
- 构建与校验链路完整：`typecheck` / `test` / `build` 三道都有。

## 3. 需要准备的东西（清单）

### A. 决策（不写代码，先拍板）

| # | 决策 | 选项 | 建议 | 影响面 |
| --- | --- | --- | --- | --- |
| A1 | 主题写法 | CSS-first `@theme` vs `@config` 引 v3 配置 | `@theme` | v4 没有 config 文件，回退等于自找麻烦 |
| A2 | 组件来源 | 自写原语 vs 引 Radix / Base UI | 先自写 5 个高频原语 | 引 UI 库能拿到焦点管理与 a11y，但样式适配成本高 |
| A3 | 主题范围 | 只做浅色 vs 预留深色 | 先只做浅色 | 决定 token 是否要成对、是否加 `dark` 变体；现有深色侧栏 ≠ 深色主题 |
| A4 | 字号基线 | 维持 12px vs 提升到 13/14 | 先维持（等价迁移） | 提升会降低一屏信息密度，属产品决策 |
| A5 | 间距策略 | 4px 网格并接受 ±1~2px 位移 vs 保留全部取值 | 4px 网格 | 不取整等于没统一；取整会让部分布局微移 |
| A6 | 断点 | 沿用现有 6 档 `max-width` vs 改移动优先 | 沿用，映射为 `max-*` 变体 | 改 `min-width` 要回归所有页面 |
| A7 | 迁移边界 | `extension/` 是否纳入 | 不纳入，仅共享色板 | 扩展是 Shadow DOM 独立样式，另立规则 |
| A8 | 文档形态 | 升级现有"视觉组件"页 vs Storybook | 升级现有页 | Storybook 要新工具链和额外构建 |
| A9 | 命名语言 | token 英文名 + 中文注释 vs 中文名 | 英文 token + 中文文档 | 影响所有代码可读性 |

### B. Token 层（`app/src/styles/theme.css`）

- [ ] B1 **颜色**：品牌 / 中性 / 语义三组，目标 ≤30 个（草案见 §4.1）。
- [ ] B2 **字体族**：`sans` / `display`（衬线）/ `mono`；决定是否自托管 Inter（当前无 webfont，引入需加文件、字体许可与首屏成本）。
- [ ] B3 **字号阶**：8 档（含行高）+ 4 档字重 + 字距；把 19 种字号收敛到 8 档。
- [ ] B4 **其余维度**：间距（4px 基数、8 档）、圆角（5 档）、阴影（4~5 档）、层级（10 档）、动效（4 档时长 + 2 条缓动）、断点（5 档）。
- [ ] B5 **兼容别名**：`--paper: var(--color-paper)` 等，保证旧 CSS 一行不改也能继续跑。
- 验收：`@theme` 中没有重复写的魔法值；旧 CSS 未改，页面截图零差异。

| `EmptyState` | `preview-empty`、`drawer-empty` | — | P2 |
| `Tooltip` | 目前无统一实现 | — | P2 |

每个原语都要先定清楚四件事：props 契约、尺寸、交互状态（hover / active / focus-visible / disabled / loading）、无障碍（`aria-*`、焦点管理、键盘）。React 19 可直接把 `ref` 当普通 prop 透传，不需要 `forwardRef`。

> 边界：维度预览、自由画板、缩放把手、画布元素这类高度定制的交互**不要**抽象成通用组件，只要求它们的颜色、字号、圆角、层级从 token 取值。

### D. 基础设施

- [ ] D1 **`cn()`**：`clsx` + `tailwind-merge`。理由：已有 100+ 处条件拼接；原语需要外部 `className` 覆盖内部默认类，没有 merge 会产生冲突类并存。
- [ ] D2 **变体组织**：先手写 variant map；变体膨胀到难维护再考虑 CVA（避免为 5 个组件引 3 个依赖）。
- [ ] D3 **动态类名策略**：禁止 `handle-${dir}` 式拼接，改为显式映射表（`const HANDLE_CLASS = { n: "top-0 ...", ... }`）；确需动态时用 v4 的 `@source inline()` 显式登记。
- [ ] D4 **格式化与类名排序**：目前没有任何 formatter。若要 `prettier-plugin-tailwindcss`（v4 兼容），会一次性重排全仓，建议单独一次提交、不与其他改动混在一起。
- [ ] D5 **守卫脚本**：`scripts/check-design-tokens.mjs` 扫描 `app/src/**/*.tsx` 中的 `#hex`、`text-[13px]` 这类任意值、内联 `style={{ color }}`，发现即失败，接入 `npm test` 或独立 `npm run check:ui`。没有守卫，收敛成果会在三个月内退化。
- [ ] D6 **目录与导入约定**：`app/src/ui/`（原语）、`app/src/styles/`（tokens / base / legacy）；可选加 `@/` 别名（需同时改 `tsconfig.json` 与 `vite.config.ts`）。
- [ ] D7 **依赖最小集**：`clsx` + `tailwind-merge`（合计约 1.5 KB gzip），其余按需。
- [ ] D8 **补齐 Tailwind 自身版本**：把 `tailwindcss` 写进 `devDependencies` 并与 `@tailwindcss/vite` 锁同一 minor（当前它只是传递依赖，`package-lock` 解析到 4.3.3，插件声明 ^4.2.1——升一次插件就可能悄悄换引擎）。

### E. 样式分层与迁移（关键，见 §5 细节）

- [ ] E1 拆分 `globals.css`：`styles/tokens.css`、`styles/base.css`、`styles/legacy/*.css`（按视图分文件）。
- [ ] E2 用 `@import "..." layer(components)` 把旧 CSS 降到 components 层，恢复 utility 的优先级。
- [ ] E3 复核 base 层：全局 `:focus-visible`、`body` 字体、滚动锁、`prefers-reduced-motion` 必须留在 base，且不被组件层的 `outline: 0` 意外压掉（`globals.css:77` 的 `.search-box input { outline: 0 }` 就是现成例子）。
- [ ] E4 **迁移单元 = 视图**，不是"类"：一次迁完一个视图并截图对比，避免半迁移状态长期共存。
- [ ] E5 顺序：视觉组件页 → 登录 / 账号 / 成员 / 令牌（结构最规整）→ 主页 → 全部素材 / 回收站 → 上传 / 详情 / 标签管理 → 维度页 → 画板与预览（交互最复杂，最后做）。
- [ ] E6 每个视图的完成定义：无新增 hex、无 `text-[Npx]`、交互状态齐全、键盘可走查、截图与迁移前一致。

## 5. 分层与迁移（技术关键点）

**现状问题**：`globals.css` 里 1,124 行规则全部在 `@layer` 之外。CSS 层叠规则是"未分层的普通声明优先于任何层"，而 Tailwind 的 utility 在 `utilities` 层。结论：**现在给旧元素加 `class="bg-accent"` 是不生效的**，因为 `.asset-card { background: var(--surface) }` 未分层，永远赢。

**解法**（最小 diff，不用手工包 1,124 行）：

```css
/* app/src/globals.css */
@import "tailwindcss";
@import "./styles/tokens.css";                 /* @theme + 兼容别名 */
@import "./styles/base.css" layer(base);       /* body、focus-visible、滚动锁 */
@import "./styles/legacy.css" layer(components); /* 现有 1,124 行原样搬过去 */
```

只需把现有内容整体移到 `legacy.css`、在入口加一行 `layer(components)`，utility 就恢复优先级。验证方式：给任一 `.primary-button` 元素临时加 `class="bg-sage"`，DevTools 中应看到 utility 生效。

**注意**：
1. `@import` 必须写在所有规则之前（`@charset` / `@layer` 语句除外）。
2. `@keyframes` 放进层里仍有效，但建议留在 `legacy.css` 原位，减少变量。
3. 搬层后 `:root` 变量、`* { box-sizing }`、`body` 规则要留在 base/tokens，不要跟着进 components。
4. `base.css` 与旧 CSS 里那些 `outline: 0` 的规则要复核：层顺序固定为 base < components，全局焦点样式可能被组件规则压掉（今天也是这个结果，但要确认这是有意为之）。

**迁移节奏**：每次只迁一个视图；迁移前先截图，迁移后逐像素对比；旧类名在迁移完成后立即删除，不做"两套并存"的过渡态（并存必然出现两边都改、越改越乱）。

## 7. 风险与对策

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| 层叠优先级倒挂 | 加了 utility 没效果，误以为 Tailwind 坏了 | 先做 E2 分层，再动任何组件 |
| 动态类名 | `handle-${dir}` 生成不出样式，裁剪后线上丢样式 | 显式映射表；必须动态时 `@source inline()` |
| 视觉漂移 | 间距取整、字号分档导致整体位移 | 先等价抽取；P3 每视图截图对比 |
| 信息密度下降 | 字号/间距统一后一屏少放内容 | 字号提升单独立项，不与重构同批 |
| 与在改文件冲突 | `DimensionPreview.tsx` 当前有未提交改动，直接大改易冲突 | 迁移从其它视图起步，画布类最后做 |
| 抽象过度 | 把 3D 场景、画布交互硬套成通用组件 | 只抽象"通用控件"，画布内部只受 token 约束 |
| 守卫缺失 | 三个月后新代码又出现 hex | D5 守卫脚本进 CI |
| 依赖膨胀 | 为 5 个组件引入 UI 框架 + 动画库 | 最小集 clsx + tailwind-merge，其余按需评估 |

## 8. 待确认的问题

1. 字号基线是否维持 12px？如果提升到 13/14px，接受一屏信息量下降吗？
2. 是否要预留深色主题？（影响 token 是否成对设计）
3. 主按钮用 `#e1512f`（白字 3.87:1）还是改用 `#b93b20`（5.66:1）？前者品牌更准，后者可读性达标。
4. 次级文字统一到 `#63685f`（5.14:1）会略微变深，设计侧是否接受？
5. 弹层层级是否统一为"模态 80 / 嵌套 90 / toast 100"？现有 80/90/100/30000 四档需要一次收口。
6. 是否引入 `clsx` + `tailwind-merge`（约 1.5 KB）？还是继续用模板字符串？
7. 文档页是继续用应用内"视觉组件"页，还是上 Storybook？
8. 是否接受一次全仓 Prettier 重排（仅为类名排序）？还是先不引入 formatter？

// app/src/ui/Button.tsx（示意）
import type { ButtonHTMLAttributes } from "react";
import { cn } from "./cn";

type Variant = "primary" | "secondary" | "ghost" | "danger";
type Size = "sm" | "md";

const VARIANT: Record<Variant, string> = {
  primary: "bg-accent text-white hover:bg-accent-strong border border-accent",
  secondary: "bg-surface text-ink border border-line hover:border-line-strong",
  ghost: "bg-transparent text-ink hover:bg-line-soft border border-transparent",
  danger: "bg-danger-soft text-danger border border-danger-border",
};

const SIZE: Record<Size, string> = {
  sm: "h-7 px-2.5 text-xs",
  md: "h-9 px-3.5 text-sm",
};

export function Button({
  variant = "secondary",
  size = "md",
  className,
  ...rest
}: ButtonHTMLAttributes<HTMLButtonElement> & { variant?: Variant; size?: Size }) {
  return (
    <button
      type="button"
      className={cn(
        "inline-flex items-center justify-center gap-1.5 rounded-md font-medium",
        "focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-accent",
        "disabled:opacity-50 disabled:pointer-events-none",
        VARIANT[variant],
        SIZE[size],
        className,
      )}
      {...rest}
    />
  );
}
