# 画板与维度预览同步机制：Figma/Linear 怎么做，本仓库为什么"跳"，以及改造方案

> 本文是 2026-11-01 的调研快照。**只做分析与方案，不改代码**；落地时再更新 `requirements/CURRENT.md` 与 `CHANGELOG.md`。
>
> 调研触发：弱网下在自由画板拖动/缩放/编辑文本、或在维度预览里拖动图片改坐标时，内容"跳着更新"、操作不跟手；怀疑是同步机制问题。
> 范围：`app/src/BoardView.tsx`（自由画板，主体）、`app/src/DimensionPreview.tsx` 与 `/api/preview-values`（维度预览的坐标拖动，见 §3.5 补充）、以及两者背后的接口与数据表。
> 目的：先回答"Figma 这种是怎么同步的、是不是先存本地再静默上传"，再给出可分期落地的改造路径与验收标准。可执行的完整方案见 `requirements/archive/2026-11-01_画板与维度预览同步改造_实施方案.md`。

## 1. 结论摘要

1. **Figma 不是"定时保存整份文件"，也不是"浏览器先存一份再批量上传"**。它是"每次操作产生一个属性级小 delta → 本地立刻生效 → WebSocket 发服务端定序 → 服务端广播给其他人 → 自己收到 ack（版本号）"。所以用户感受到的"异步、静默"是对的，但**关键不是异步**，而是三条硬约束：本地状态永不回退、未确认的本地变更不被快照覆盖、传输的是"变更"而不是"快照"。
2. **"跳"的根因不是渲染性能，是同步协议**：本仓库用「900ms 全量快照轮询 + 整数组替换」，而保存是「N 个元素 = N 个串行请求」。两者叠加，慢网下快照回包会稳定地落在保存中途，把已拖好的元素覆盖回旧位置，随后下一次轮询再跳回来。
3. **最致命的一处是版本号语义**：`canvas.revision` 只在**全部** PATCH 完成后才写回本地（`BoardView.tsx:933`），但服务端每成功 PATCH 一个元素就已经 bump 了 revision（`routes.js:794-798`）。于是保存过程中的轮询回包 revision 必然"更新"，从而通过 `data.canvas.revision > canvas.revision` 这道唯一防线（`BoardView.tsx:304`），用**半保存状态**覆盖本地全场。
4. **还有一个可复现的隐性跳变**：轮询的守卫条件在**发请求时**判断 `interaction.current`/`panRef` 等（`BoardView.tsx:384`），但 HTTP 回包要 200~800ms 才到，回包时不复判。空闲时发出的请求完全可能在用户按下并拖动之后才落地，于是拖到一半被整表替换。
5. **`revision` 用 `Date.now()` 生成**（`routes.js:795`），同毫秒两次写入值相等，`>` 比较会漏判；它也不是逻辑版本，无法表达"某元素自某版本后变了"。
6. **保存失败的处理方式放大了抖动**：失败只 toast，然后 `loadCanvas()` 全量重载（`BoardView.tsx:937`），等于把用户刚摆好的位置整块退回服务器旧状态。弱网下这是"跳"的第二大来源。
7. **改造分三级**：P0 止血（请求代际 + 保存期间禁轮询 + 批量接口 + 失败不回滚）；P1 本地优先队列（items 为唯一真相、dirty 合并、IndexedDB 草稿、重试与同步状态）；P2 增量同步/实时广播（`since` 参数 + SSE）。**不需要** CRDT。2026-11-01 决策：因一人使用、别人偶尔打开看，**P2 的增量与实时不做**，改为"进入/切回时拉取 + 30 秒兜底"；Frame 上服务端要做。
8. **顺带发现（与本问题相关但独立）**：Frame 不存服务端，只存浏览器 `localStorage`（`BoardView.tsx:268-271`）。同类画板在两台机器/两个浏览器上看到的 Frame 完全不同，这既是数据隐患，也让"同步"的语义更难解释。

## 2. Figma / Linear 实际是怎么同步的

### 2.1 一句话模型

> 客户端持有一份完整文档的内存副本，所有编辑**先在自己身上生效**，同时把「这个对象的这个属性变成了这个值」发给服务端；服务端给操作定一个全局顺序并广播，客户端收到别人的操作（或自己的 ack）后合并进本地副本。**任何时刻网络只决定"别人多久看到"，不决定"我自己看到什么"。**

### 2.2 拆开看五个要件

| 要件 | Figma | Linear | 本仓库现状 |
| --- | --- | --- | --- |
| 本地权威副本 | 有（内存文档树 + 浏览器 IndexedDB 缓存） | 有（IndexedDB 全量镜像） | **无**：`items` 是 React state，刷新即丢，以服务器为准 |
| 乐观应用 | 有，操作即时生效，不等网络 | 有，mutation 先本地应用 | 有（`setItems` 逐帧更新），但保存落点前的"确认"完全依赖回包 |
| 传输单位 | 属性级 delta（一个小 patch） | 行级 mutation（insert/update/delete 队列） | **整对象 / 整画板快照**（GET 全量、PATCH 单元素全字段） |
| 服务端定序 | 每个文件的 multiplayer 进程持有内存态并定序，客户端收 ack | 服务端分配同步序列号 | 无：`revision` 只是整板时间戳，不回传"你这次操作属于第几版" |
| 冲突处理 | 同属性后写覆盖 + 本地未确认变更浮在上层（rebase） | 同理，队列在服务端状态上重放 | 无：后到的全量快照直接覆盖，谁快谁赢 |
| 持久化 | 内存态 + 周期 checkpoint + append-only journal，崩溃用 journal 重放 | 服务端持久化 + 客户端 IndexedDB 缓存 | SQLite 每次写直接落盘（这点反而最稳） |

Figma 官方在《Making multiplayer more reliable》里描述的就是"权威 multiplayer 服务 + WebSocket 更新路径 + checkpoint/journal 双写"这套结构：<https://www.figma.com/blog/making-multiplayer-more-reliable/>。Linear 的同步引擎在公开演讲《Scaling the Linear Sync Engine》里讲得更直白——本地库 + 变更队列 + 服务端增量：<https://linear.app/now/scaling-the-linear-sync-engine>。

### 2.3 为什么"整表轮询"必然跳

把上面抽象成不变量：

1. **快照只能用于"补历史"，不能用于"覆盖现在"**。任何一次全量替换，都必须先证明"本地没有比它更新的东西"。
2. **未确认的本地变更优先于一切服务端状态**。远程/快照只能更新"本地没有脏数据的字段"。
3. **版本号必须能在"回包时"被检验**，而不是"发请求时"。

本仓库三条都破了，且是组合破的——单看每一条都像"小瑕疵"。

## 3. 本仓库现状：一次拖动到底发生了什么

### 3.1 时序（弱网，RTT≈400ms，选中 6 张图拖动）

```
t=0      pointerdown  → interaction.current = {...}
t=0~900  pointermove  → setItems(...)              本地渲染，顺滑 ✓
t=900    轮询定时器触发 → 因 interaction.current 非空，跳过 ✓
t=1200   pointerup    → interaction.current = null
                       savingRef++ → 逐条 await PATCH（6 次 RTT ≈ 2.4s）
t=1250   轮询触发 → 守卫已全部为 null，savingRef 未检查 → 发出 GET
t=1650   GET 回包：服务端此时只保存了第 1 个元素，
         revision 已被 bump（比本地 canvas.revision 新）
         → onlyIfNewer 通过 → setItems(半保存快照)      ← 元素跳回原位
t=3600   6 条 PATCH 全部完成 → setCanvas(revision)      ← 只更新版本，不修 items
t=4500   下一轮 GET → setItems(正确快照)                ← 元素跳回终点
```

**"跳着更新、不跟手"就是 t≈1650 与 t≈4500 这两次回跳。** 拖动本身（`pointermove` 只改本地 state，不发请求，见 `BoardView.tsx:864-904`）是流畅的。

### 3.2 逐条证据

| # | 问题 | 位置 | 说明 |
| --- | --- | --- | --- |
| A | 全量快照替换 | `BoardView.tsx:301-306` | `loadCanvas` 只做 `setItems(data.items)`，没有"保留本地脏元素"的概念 |
| B | 守卫在发请求时判断 | `BoardView.tsx:381-387` | 回包时不复判交互/保存状态，也不丢弃乱序响应 |
| C | 保存期间不禁轮询 | 同上 | 条件里有 `interaction`/`pan`/`frameMove`/`frameResize`/`draw`/`frameDraw`/`batch`，**唯独没有 `savingRef`** |
| D | revision 全部保存完才写回本地 | `BoardView.tsx:926-933`、`1184-1191`、`644-651`、`662-669` | 保存窗口内本地版本号"落后于"服务端，防线失效 |
| E | 逐元素串行 PATCH | `BoardView.tsx:929-932`、`1187-1190`、`647-650`、`665-668`、`1323-1326` | N 个元素 = N 个 RTT，窗口被拉长到秒级 |
| F | 失败即全量回滚 | `BoardView.tsx:934-937` | 一次超时就把整板退回服务器状态，且清掉撤销项 |
| G | revision 非单调 | `routes.js:794-798` | `Date.now()` 同毫秒相等；也不是逻辑版本，无法做增量 |
| H | 无批量、无增量、无 ETag | `routes.js:836-864` | PATCH/DELETE 各一次往返、各 bump 一次；GET 永远全量 |
| I | 无本地草稿、无重试队列 | 全局 | 刷新即丢；断网期间的操作直接丢失 |
| J | 归一化副作用可能自激 | `BoardView.tsx:332-371` | 快照落地 → effect 发现 `parentFrameId` 与几何推导不一致 → 再 PATCH 一轮 → revision 再变 → 又触发轮询 |

补充两点事实：

- **服务端是单进程同步式 SQLite**，`getCanvas` 的 canvas 查询与 items 查询在同一 tick 内完成（`routes.js:772-792`），所以**单次 GET 内部是一致的**；问题不在服务端一致性，而在"客户端拿旧快照覆盖新本地"。
- **写接口静默 clamp**：`zIndex` 上限 10000、坐标为整数等（`routes.js:822-828`、`843-851`）。服务端不会回传归一化后的对象，本地保留的是"我以为的样子"，这与服务器可能永久不一致——只是目前量级小、没被察觉。

### 3.3 已经存在的正确做法（可复用）

`DimensionPages.tsx:133-141` 的 `selectAxes` 已经是"本地立即更新 + 串行队列提交"：

```ts
onPageChange({ ...current, selectedIds });        // 本地先生效
axesQueue.current = axesQueue.current
  .catch(() => {})
  .then(() => apiFetch("/api/preview-pages", { method: "PATCH", body: ... }));
```

这条思路就是 P1 的种子：**把"串行队列"从单个视图提升为画板的通用写队列，并补上 dirty 标记与重试**。

### 3.4 怎么快速复现（给验收用）

1. DevTools → Network → 自定义限速：RTT 400ms、下行 400kbps、丢包 0~5%。
2. 框选 5~8 个元素，连续拖动，**每次松手后 1 秒内立刻再拖**。
3. 观察：每次松手后元素会先回跳、再跳回；拖动过程中偶发"被拽回"的顿挫。
4. 把 `loadCanvas` 临时加一行 `console.debug("[board] snapshot", data.canvas.revision, data.items.length)`（P1 落地时删掉），可看到快照在 `savingRef > 0` 期间仍然落地。

### 3.5 追加：维度预览的坐标拖动（同日补充）

维度预览不是"另一套完全不同的东西"，而是同一套模型里**更简单的一档**——一次只写一张图的几个坐标，没有整页快照轮询。但它同样会跳，机制不同：

- **没有版本号**：`PATCH /api/preview-values` 只回 `{ok:true}`（`preview-pages.js:179-188`），`preview_pages` 也没有 revision 列，客户端无法判断回包新旧，更无法丢弃过期写入。
- **同一坐标并发写按"到达顺序"落地**：每键一次 `UPDATE`（`:185`）。连续快速拖同一张图（A→B）时，慢网下 PATCH(A) 可能后到，最终库里的值是 A，界面显示 B —— 刷新即回跳。
- **失败即整页重取**：`ArtDatabaseApp.tsx:528/574` 的 `setPreviewRevision++` 会让 `DimensionPages` 重取整页，把本地乐观值换回服务器旧值，`overrides` 又被清空，于是"松手后先对、再跳回"。
- **每次保存弹 toast**（`App:525/570`）：连续拖动刷屏，与"静默同步"相反。
- **预览页完全没有刷新机制**：全仓库 `setInterval` 只有画板的 900ms 与删除倒计时，别人改了坐标只能靠手动切页才看得到。
- **乐观值（`overrides`）与权威值（`previewPage`）两套并存**，靠时序巧合对齐；任何整页重取都可能让两者错位。

结论：预览需要的不是"缩小版画板方案"，而是**同一套 outbox 内核 + 一个按键（素材+维度）的适配器**：同样本地先定稿、按 150ms 合并、串行提交、失败重试、按 `lastRev` 合并、状态点提示。详见实施方案 §3.3 / §4.5.3 / §6.3 / §6.8。

## 4. 目标模型

```
        ┌───────────── 本地唯一真相（items / frames） ─────────────┐
UI 事件 →│ setState 立即生效 → dirty.add(id) → 入队（按 id 合并）  │
        └───────────────────────┬──────────────────────────────┘
                                │ flush（串行 or 单批）
                                ▼
                    POST /api/canvas-items/batch
                                │ 返回 { revision, items: 归一化后 }
                                ▼
              ack：dirty.delete(id)、记录 serverRev、写回归一化值
                                │
        GET /api/canvas?canvasId（仅在 idle 且无 dirty 时应用；进入/切回/30s）
        （备选，本轮不做）P2：SSE 推送 { revision, changedIds } → 只合并非 dirty 元素
```

四条不变量（写进代码，也写进测试）：

1. **本地状态只增不减**：任何网络回包不得让"用户刚摆放的对象"回到旧位置。
2. **快照合并按元素 id + 版本**：dirty 元素一律保留本地值；非 dirty 元素接受服务端值。
3. **版本校验发生在回包时刻**，用请求代际（generation）丢弃乱序响应。
4. **失败不销毁本地**：进重试队列 + 顶部"未同步"状态点，恢复后自动补齐。

## 5. 分阶段方案

### 5.1 P0：止血（不改数据模型）

目标：弱网下松手后**不再回跳**。改动集中在 `BoardView.tsx` + 一个新接口。

1. **请求代际**：`const fetchSeq = useRef(0)`；`loadCanvas` 进入时 `const seq = ++fetchSeq.current`，`await` 之后 `if (seq !== fetchSeq.current) return;`。丢弃乱序/过期回包。
2. **回包时复判**：await 之后再判断 `interaction.current || frameMoveRef.current || frameResizeRef.current || drawRef.current || savingRef.current > 0 || dirtyRef.current.size`，任一为真就**放弃本次快照**（保留本地）。
3. **轮询补 `savingRef`**：`BoardView.tsx:384` 的条件里加 `savingRef.current === 0`。
4. **批量接口**：新增 `POST /api/canvas-items/batch`，body `{ canvasId, items: [...] }`，一个 SQLite 事务内逐条 UPDATE、最后 `bumpRevision` 一次，返回 `{ revision, items }`（回传服务端归一化值）。把 5 处逐条 PATCH 循环（`648`、`666`、`930`、`1188`、`1324`）换成一次调用。
5. **失败不回滚**：去掉 `catch` 里的 `loadCanvas(canvas.id)`，改为"保留本地 + 入重试队列"，仅当用户主动刷新/切换 Page 才以服务器为准。
6. **revision 改自增**：`UPDATE canvases SET revision = revision + 1`。现网旧值是 13 位 `Date.now()`，继续自增仍是单调的，**无需迁移**。

预期效果：松手后最多一次批量 RTT（而非 N 次），且保存期间不再有任何快照能落地；弱网下松手即定稿。

### 5.2 P1：本地优先写队列（推荐主线）

1. **抽出 `useCanvasSync(canvasId)`**：内部持有 `items`、`frames`、`dirty: Set<id>`、`queue: Map<id, patch>`、`serverRev`、`status: "synced" | "saving" | "offline"`。
2. **合并（coalesce）**：同一元素在同一帧内的多次移动只保留最后一次（拖动本来只在松手后入队，天然合并）；文本输入用 300ms 空闲提交。
3. **落盘草稿**：队列与 dirty 快照写 `localStorage`（画板 items 规模在百级，JSON 足够；要更大再上 IndexedDB）。刷新后可恢复并重放。
4. **重试**：指数退避 1s/2s/4s/8s，最多 5 次；`navigator.onLine` + `online` 事件触发立即 flush。
5. **状态指示**：右下角小圆点（灰=已同步、黄=保存中、红=未同步），替代现在"失败才 toast"的被动模式。**这就是 Figma 的"静默"——不是没有状态，而是状态不打扰。**
6. **快照合并**：`loadCanvas` 改为 `mergeSnapshot(data.items)`，跳过 dirty 元素；非 dirty 元素按 `serverVersion` 比较后再覆盖。
7. **契约**：`GET /api/canvas` 增加每个元素的 `lastRev`（`canvas_items` 加 `last_rev INTEGER NOT NULL DEFAULT 0`，写入时记本次 `revision`）；旧字段不动，向后兼容。

### 5.3 P2：增量同步 + 实时（按需）

> **决策（2026-11-01）**：实际是"一人使用、别人偶尔打开看"，因此**本轮不做 §5.3 的增量与实时**；改为"进入/切回页面时拉一次 + 停留 30 秒兜底"。以下保留为备选设计，实施计划见 `requirements/archive/2026-11-01_画板与维度预览同步改造_实施方案.md` §13。Frame 上服务端则已确认要做，并入该计划的 P1。

- **`GET /api/canvas?canvasId=...&since=123`**：只返回 `last_rev > since` 的元素 + `deletedIds`（需要 tombstone 表或软删列）。适合"同一画板长时间打开"的场景，把每次 900ms 的全量 JSON 换成小 delta。
- **SSE 广播**（比 WS 省事，Node 单进程用 `Map<canvasId, Set<res>>` 即可）：写操作后推 `{ revision, changedIds }`，客户端收到后按 §5.2 合并。解决"两个标签页/两个人同时看"的 900ms 延迟与互相覆盖。
- **Frame 上服务端**：现在 Frame 只在 `localStorage`，建议并入画板文档（`canvases.frames` JSON 列或独立表），否则"同步"永远少一半内容。

### 5.4 明确不做

- **不上 CRDT（Yjs/Automerge）**：本产品是"团队共享素材库 + 单人为主编辑画板"，冲突是"同一元素位置后写覆盖"，LWW + 队列完全够；CRDT 会把数据结构、序列化、调试成本抬一个量级，收益只在"两人同时拖同一张图"这种边缘场景。
- **不做"整板 JSON 存 blob"**：会锁死将来做增量的能力，且每次改一个坐标要写整份文档。
- **不改 `GET /api/canvas` 的既有语义**：`since`、`version` 都是**可选/新增**字段，符合 AGENTS 的 URL 契约约束。

## 6. 验收标准

| 场景 | 判据 |
| --- | --- |
| 限速 400ms RTT，连续拖动 20 次 | 松手后元素位置**零回跳**；最终位置与刷新后一致 |

## 7. 风险与取舍

| 风险 | 说明 | 处理 |
| --- | --- | --- |
| revision 语义变化 | `Date.now()` → 自增，旧值仍是 13 位大数，单调性保持 | 无需迁移；文档写清"客户端只做大小比较，不解释数值含义" |
| 批量接口的事务边界 | 一批 8 个元素里某条 404 时，整批回滚还是部分成功？ | 选**整批回滚**并返回失败 id 列表，客户端只对失败项重试 |
| 本地草稿与服务器分叉 | 用户在两台机器上编辑同一 Page | LWW + 后写入者覆盖；`version` 冲突时保留本地并提示一次"已用本机版本覆盖" |
| 静默 clamp 造成的长期分叉 | `zIndex`、坐标取整 | 批量接口回传服务端归一化后的 item，客户端直接采纳（P1 第 6 点） |
| 900ms 轮询保留期 | P0 阶段仍轮询，只是加了守卫 | 明确它只是过渡；P1 后改为"进入/切回/聚焦拉取 + 30s 兜底" |
| Frame 存本地 | 换机器就丢布局，且与 items 的 `parentFrameId` 可能对不上（会触发 §3.2 J 的自激） | 已确认要改：随 P1 把 Frame 迁到服务端（整份数组 LWW） |
